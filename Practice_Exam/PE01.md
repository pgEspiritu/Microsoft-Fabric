# Question 1

## Question

You have a Fabric workspace that contains a lakehouse named **Lakehouse1**.

A user named **User1** plans to use **Lakehouse explorer** to read **Lakehouse1** data.

You need to assign a workspace role to **User1**. The solution must follow the principle of least privilege.

**Which workspace role should you assign to User1?**

> Select only one answer.

- Admin
- Contributor
- Member
- Viewer

---

## Answer

**✅ Contributor**

---

## Explanation

The **Contributor** workspace role is the correct answer because **Lakehouse explorer requires Contributor permissions** to access and browse lakehouse data. Although User1 only needs to read data, the **Viewer** role does not provide sufficient permissions to use Lakehouse explorer.

The **Contributor** role grants the minimum level of access required to work with Lakehouse explorer while avoiding the broader management permissions provided by the **Member** and **Admin** roles. Therefore, it satisfies the **principle of least privilege**.

### Why the other options are incorrect

- ❌ **Admin**
  - Provides full administrative control over the workspace, including managing users and workspace settings.
  - Exceeds the permissions required.

- ❌ **Member**
  - Can create, edit, publish, and share workspace content.
  - Grants more permissions than necessary.

- ❌ **Viewer**
  - Provides read-only access to workspace items.
  - **Cannot use Lakehouse explorer** to browse and read lakehouse data.

---

## Key Exam Tip

For Microsoft Fabric exam questions, remember:

- **Viewer** = View workspace items only.
- **Contributor** = Can use **Lakehouse explorer** and interact with lakehouse data.
- **Member** = Can create, publish, and share content.
- **Admin** = Full workspace management.

If a question specifically mentions **using Lakehouse explorer**, the correct answer is typically **Contributor**.

# Question 2

## Question

Your company uses Microsoft Fabric for data analytics. You must protect sensitive data from unauthorized access in the data warehouse.

You need to manage access to specific objects in the warehouse.

**What action should you take to achieve this?**

> Select only one answer.

- Set item-level permissions to warehouse.
- Configure dynamic data masking on objects.
- Use TSQL to grant granular permissions.
- Implement row-level security for objects.

---

## Answer

**✅ Use TSQL to grant granular permissions.**

---

## Explanation

The correct answer is **Use TSQL to grant granular permissions** because Microsoft Fabric Data Warehouse supports **object-level security** through Transact-SQL (T-SQL). You can use SQL statements such as **GRANT**, **DENY**, and **REVOKE** to control access to specific database objects, including tables, views, schemas, and stored procedures.

This approach allows administrators to precisely manage who can access individual warehouse objects, making it the appropriate solution for protecting sensitive data from unauthorized access.

### Why the other options are incorrect

- ❌ **Set item-level permissions to warehouse**
  - Item-level permissions control access to the **warehouse item** in the Fabric workspace, not individual database objects within the warehouse.

- ❌ **Configure dynamic data masking on objects**
  - Dynamic Data Masking (DDM) hides sensitive data from certain users but **does not prevent access** to the objects themselves. Users can still query the tables if they have permission.

- ❌ **Implement row-level security for objects**
  - Row-Level Security (RLS) restricts **which rows** a user can see within a table.
  - It does **not** control access to specific warehouse objects such as tables or views.

---

## Key Exam Tip

Remember the different security levels in Microsoft Fabric Data Warehouse:

- **Workspace permissions** → Access to the Fabric item.
- **T-SQL GRANT/DENY/REVOKE** → Access to specific database objects (tables, views, schemas, procedures).
- **Row-Level Security (RLS)** → Restricts rows returned from a table.
- **Dynamic Data Masking (DDM)** → Masks sensitive column values without restricting object access.

If the question asks about **managing access to specific warehouse objects**, the answer is **T-SQL granular permissions**.

# Question 3

## Question

Your company is using Microsoft Fabric to manage its data warehousing needs. The data includes sensitive customer information that must be protected according to regulatory requirements.

You need to protect sensitive data from unauthorized access while allowing authorized users to perform their tasks efficiently.

**Each correct answer presents part of the solution. Which three actions should you take?**

> Select all answers that apply.

- Apply sensitivity labels.
- Grant all users Viewer role.
- Implement object-level security.
- Revoke all user permissions temporarily.
- Use Microsoft Entra ID groups for user permissions.

---

## Answers

- ✅ Apply sensitivity labels.
- ✅ Implement object-level security.
- ✅ Use Microsoft Entra ID groups for user permissions.

---

## Explanation

To protect sensitive customer information while ensuring authorized users can perform their work, Microsoft Fabric provides multiple complementary security features.

### ✅ Apply sensitivity labels

Sensitivity labels classify and protect sensitive data across Microsoft Fabric. They help enforce organizational and regulatory policies by identifying data based on its level of sensitivity. Labels can also integrate with Microsoft Purview and Microsoft Information Protection to help safeguard data throughout its lifecycle.

### ✅ Implement object-level security

Object-level security restricts access to specific warehouse objects, such as tables, views, and schemas. In Microsoft Fabric Data Warehouse, this is typically implemented using **T-SQL** commands such as **GRANT**, **DENY**, and **REVOKE**, ensuring users can access only the objects they are authorized to use.

### ✅ Use Microsoft Entra ID groups for user permissions

Assigning permissions through **Microsoft Entra ID groups** simplifies security management by granting access to groups rather than individual users. This approach improves scalability, reduces administrative effort, and supports the principle of least privilege.

---

## Why the other options are incorrect

- ❌ **Grant all users Viewer role**
  - Assigning every user the Viewer role does not satisfy security requirements because different users require different levels of access. Permissions should be assigned based on roles and business needs rather than giving everyone the same workspace role.

- ❌ **Revoke all user permissions temporarily**
  - Temporarily removing all permissions does not provide an effective or sustainable security solution. It prevents authorized users from performing their work and is not a recommended security practice.

---

## Key Exam Tip

Microsoft Fabric security operates at multiple layers:

- **Sensitivity labels** → Classify and protect sensitive data.
- **Object-level security** → Restrict access to database objects (tables, views, schemas).
- **Microsoft Entra ID groups** → Simplify permission management through group-based access.
- **Workspace roles** → Control access to Fabric items.
- **Row-Level Security (RLS)** → Restrict rows within tables.
- **Column-Level Security (CLS) / Dynamic Data Masking (DDM)** → Protect sensitive columns.

For questions asking how to **protect sensitive data while enabling authorized access**, expect a combination of **classification**, **access control**, and **identity-based permission management**.

# Question 4

## Question

Your company is using Microsoft Fabric to manage its data analytics solutions. The IT department needs to ensure that sensitive data is protected and only accessible to authorized personnel.

You need to implement security measures to safeguard sensitive data at different levels within the data warehouse.

**Each correct answer presents part of the solution. Which three actions should you perform?**

> Select all answers that apply.

- Apply sensitivity labels.
- Assign all users to the Admin role.
- Configure workspace roles.
- Enable public access.
- Configure object-level security.
- Use role-based access control.

---

## Answers

- ✅ Apply sensitivity labels.
- ✅ Configure workspace roles.
- ✅ Configure object-level security.

---

## Explanation

Microsoft Fabric secures data through multiple layers of protection.

### ✅ Apply sensitivity labels

Sensitivity labels classify sensitive data and help protect it according to organizational and regulatory requirements. They integrate with Microsoft Purview and Microsoft Information Protection to support data governance and compliance.

### ✅ Configure workspace roles

Workspace roles (**Admin**, **Member**, **Contributor**, and **Viewer**) determine what actions users can perform within a Fabric workspace. Assigning the appropriate role ensures users have only the permissions they need, following the **principle of least privilege**.

### ✅ Configure object-level security

Object-level security restricts access to specific warehouse objects such as tables, views, and schemas. In Fabric Data Warehouse, this is implemented using **T-SQL** permissions (for example, **GRANT**, **DENY**, and **REVOKE**) to ensure users can access only authorized objects.

---

## Why the other options are incorrect

- ❌ **Assign all users to the Admin role**
  - Grants excessive permissions and violates the principle of least privilege.

- ❌ **Enable public access**
  - Makes sensitive data accessible to unauthorized users and weakens security.

- ❌ **Use role-based access control**
  - Although RBAC is a general security concept used throughout Microsoft services, the question specifically asks for actions within Microsoft Fabric. **Configuring workspace roles** is the Fabric-specific implementation of role-based access and is the expected exam answer.

---

## Key Exam Tip

For DP-700/DP-600 exams, remember the three primary security layers in Microsoft Fabric:

- **Workspace roles** → Control access to Fabric items.
- **Object-level security** → Control access to tables, views, and schemas.
- **Sensitivity labels** → Classify and protect sensitive data for governance and compliance.

When both **RBAC** and **Configure workspace roles** appear as options, Microsoft exams typically expect **Configure workspace roles**, since it is the concrete Fabric feature used to implement access control.

# Question 5

## Question

Your organization uses Microsoft Fabric for data analytics. The team must protect sensitive data in a Fabric data warehouse from unauthorized access.

You need to limit data access based on different user roles and ensure to follow the principle of least privilege.

**Which two actions should you take to achieve this solution?**

> Select all answers that apply.

- Implement column-level security.
- Assign workspace roles.
- Implement row-level security.
- Set item-level permissions.
- Use dynamic data masking.

---

## Answers

- ✅ Implement column-level security.
- ✅ Implement row-level security.

---

## Explanation

To protect sensitive data in a Microsoft Fabric data warehouse while following the **principle of least privilege**, you should implement security at the **data level**.

### ✅ Implement column-level security

Column-Level Security (CLS) restricts access to specific columns within a table. Users can query the table but will only be able to view the columns they are authorized to access. This is useful for protecting sensitive fields such as salaries, Social Security numbers, or customer personal information.

### ✅ Implement row-level security

Row-Level Security (RLS) restricts which rows a user can access based on defined security rules. Different users can query the same table while seeing only the rows they are authorized to view, such as records for their department, region, or business unit.

Together, **CLS** and **RLS** provide fine-grained access control, ensuring users see only the data required for their role.

---

## Why the other options are incorrect

- ❌ **Assign workspace roles**
  - Workspace roles control access to Fabric workspace items (such as warehouses, lakehouses, and reports), not which rows or columns of data users can view.

- ❌ **Set item-level permissions**
  - Item-level permissions determine who can access a Fabric item but do not provide fine-grained control over data within warehouse tables.

- ❌ **Use dynamic data masking**
  - Dynamic Data Masking (DDM) obscures sensitive values but does not restrict access to the underlying data. Users with sufficient privileges can still retrieve the actual values.

---

## Key Exam Tip

Different Fabric security features operate at different levels:

| Security Feature | Controls |
|------------------|----------|
| Workspace roles | Access to Fabric items |
| Item-level permissions | Access to specific Fabric items |
| Row-Level Security (RLS) | Which **rows** users can view |
| Column-Level Security (CLS) | Which **columns** users can view |
| Dynamic Data Masking (DDM) | Masks sensitive values without restricting access |

**Rule of thumb for the exam:**

- If the question asks **"who can access the warehouse?"** → Think **workspace roles** or **item-level permissions**.
- If it asks **"what data can users see?"** → Think **Row-Level Security (RLS)** and **Column-Level Security (CLS)**.

# Question 6

## Question

A company uses Microsoft Fabric for data warehousing, and there is a need to ensure that only authorized users can access specific objects within the warehouse.

You need to implement access controls for these objects.

**Each correct answer presents part of the solution. Which two actions should you perform?**

> Select all answers that apply.

- Assign item-level permissions.
- Configure row-level security.
- Implement object-level security.
- Assign workspace roles.

---

## Answers

- ✅ Assign item-level permissions.
- ✅ Implement object-level security.

---

## Explanation

To control access to specific objects in a Microsoft Fabric warehouse, you should configure permissions at both the **Fabric item level** and the **warehouse object level**.

### ✅ Assign item-level permissions

Item-level permissions control access to specific Fabric items, such as a warehouse, lakehouse, report, or semantic model. This ensures that only authorized users can access the warehouse item itself.

For example, administrators can grant users or groups access to a specific warehouse without giving them access to all items in the workspace.

### ✅ Implement object-level security

Object-level security provides more granular control within the warehouse by restricting access to specific database objects, such as:

- Tables
- Views
- Schemas

This allows administrators to control which users can access specific objects using permissions such as **GRANT**, **DENY**, and **REVOKE**.

---

## Why the other options are incorrect

- ❌ **Configure row-level security**
  - Row-Level Security (RLS) controls which rows a user can see within a table.
  - It does not control access to warehouse objects themselves.

- ❌ **Assign workspace roles**
  - Workspace roles (**Admin, Member, Contributor, Viewer**) control permissions at the workspace level.
  - They are broader permissions and do not provide specific object-level access control within the warehouse.

---

## Key Exam Tip

For Microsoft Fabric security questions:

| Requirement | Correct Feature |
|---|---|
| Access to a Fabric item (warehouse, lakehouse, report) | Item-level permissions |
| Access to tables, views, schemas | Object-level security |
| Restrict specific rows | Row-level security |
| Restrict specific columns | Column-level security |
| Manage workspace access | Workspace roles |

When the question says **"specific objects within the warehouse"**, think:

✅ **Item-level permissions + Object-level security**

# Question 7

## Question

You use Microsoft Power BI Desktop to create a Power BI semantic model.

You need to recommend a solution to collaborate with another Power BI modeler. The solution must ensure that you can both work on different parts of the model simultaneously. The solution must provide the most efficient and productive way to collaborate on the same model.

**What should you recommend?**

> Select only one answer.

- Save your work as a PBIX file and email the file to the other modeler.
- Save your work as a PBIX file and publish the file to a Fabric workspace. Add the other modeler as member to the workspace.
- Save your work as a PBIX file to Microsoft OneDrive and share the file with the other modeler.
- Save your work as a Power BI Project (PBIP). Initialize a Git repository with version control.

---

## Answer

✅ **Save your work as a Power BI Project (PBIP). Initialize a Git repository with version control.**

---

## Explanation

The correct answer is **Power BI Project (PBIP) with Git version control** because it enables multiple Power BI developers to collaborate on the same semantic model efficiently.

A **PBIP** separates the Power BI project into individual files (such as model metadata, reports, and configuration files) instead of storing everything in a single binary **PBIX** file. These files can be managed using source control systems like **Git**, allowing multiple modelers to:

- Work on different parts of the semantic model simultaneously.
- Track changes.
- Review and merge updates.
- Resolve conflicts.
- Maintain version history.

This provides the most efficient and productive collaboration experience for Power BI model development.

---

## Why the other options are incorrect

### ❌ Save your work as a PBIX file and email the file to the other modeler

- A PBIX file is a single packaged binary file.
- Only one person can effectively edit the model at a time.
- Email-based sharing creates multiple copies and makes version control difficult.

---

### ❌ Save your work as a PBIX file and publish the file to a Fabric workspace. Add the other modeler as member to the workspace

- A Fabric workspace allows collaboration and sharing of Power BI content.
- However, multiple developers cannot simultaneously edit the same PBIX semantic model in Power BI Desktop.
- Workspace permissions do not provide source-controlled model development.

---

### ❌ Save your work as a PBIX file to Microsoft OneDrive and share the file with the other modeler

- OneDrive provides file synchronization and sharing.
- However, PBIX files are still single binary files and do not support efficient simultaneous development.
- Changes from multiple users can overwrite each other.

---

## Key Exam Tip

For Power BI collaboration questions:

| Requirement | Recommended Solution |
|---|---|
| Share a finished report/model | PBIX + Fabric workspace |
| Store and sync a file | OneDrive/SharePoint |
| Multiple developers working on the same model | **PBIP + Git** |
| Source control and collaboration | **Power BI Project (PBIP)** |

When the question mentions:

- "work simultaneously"
- "different parts of the model"
- "version control"
- "collaborate with another modeler"

The expected answer is:

✅ **PBIP + Git repository**

# Question 8

## Question

You have a semantic model that loads data from an Azure SQL database and is synced via Fabric deployment pipelines to three workspaces named **Development**, **Test**, and **Production**.

You need to reduce the size of the query requests sent to the Azure SQL database when full semantic model refreshes occur in the **Development** or **Test** workspaces**.**

**What should you do for the deployment pipeline?**

> Select only one answer.

- Add a parameter to filter the data.
- Configure row-level security (RLS).
- Connect either workspace to an Azure Data Lake Storage Gen2 account.
- Configure incremental refresh.

---

## Answer

✅ **Add a parameter to filter the data.**

---

## Explanation

The correct answer is **Add a parameter to filter the data** because deployment pipelines support using **parameters** to customize data sources and queries across different environments.

In this scenario:

- The **Development** and **Test** workspaces do not require the full production dataset.
- A parameter can be used to filter the data loaded into the semantic model during refreshes.
- This reduces the amount of data queried from the Azure SQL database.
- The Production workspace can use a different parameter value to load the complete dataset.

For example:

- Development → Load only recent records or sample data.
- Test → Load a limited dataset for validation.
- Production → Load the full dataset.

This reduces query size and improves refresh performance.

---

## Why the other options are incorrect

### ❌ Configure row-level security (RLS)

- RLS controls which rows users can view after authentication.
- It does not reduce the amount of data retrieved during a semantic model refresh.
- Refresh operations are performed by the dataset/service account, not end users.

---

### ❌ Connect either workspace to an Azure Data Lake Storage Gen2 account

- Azure Data Lake Storage Gen2 is a storage solution and does not directly reduce the size of SQL queries generated during semantic model refreshes.
- It does not address filtering data between Development, Test, and Production environments.

---

### ❌ Configure incremental refresh

- Incremental refresh reduces refresh processing by loading only new or changed data partitions.
- However, the question specifically asks about **reducing query request size for full semantic model refreshes in Development or Test workspaces**.
- The recommended deployment pipeline solution is to use **parameters to filter data by environment**.

---

## Key Exam Tip

For Microsoft Fabric deployment pipelines:

| Requirement | Recommended Feature |
|---|---|
| Different data sizes per environment | ✅ Parameters |
| Restrict user data visibility | Row-Level Security (RLS) |
| Reduce refresh of historical data | Incremental refresh |
| Move/store data | Data Lake Storage |

When the question mentions **Development/Test needing smaller datasets than Production**, think:

✅ **Deployment parameters with data filtering**

# Question 10

## Question

You have a Fabric workspace named **Sales-Dev** in the **West US Azure region** that contains a lakehouse and a Microsoft Power BI semantic model.

You have an **Azure DevOps Git repository** located in the **West Europe Azure region**.

You need to connect the workspace to the repository.

**What should you do?**

> Select only one answer.

- Create a workspace identity.
- Disable workspace outbound protection.
- Update the workspace region to match the repository region.
- Enable the tenant setting that allows exporting items to Git repositories in other geographical locations.

---

## Answer

✅ **Enable the tenant setting that allows exporting items to Git repositories in other geographical locations.**

---

## Explanation

The correct answer is **Enable the tenant setting that allows exporting items to Git repositories in other geographical locations** because Microsoft Fabric requires a tenant-level setting to allow **cross-geo Git integration**.

In this scenario:

- The Fabric workspace is located in **West US**.
- The Azure DevOps Git repository is located in **West Europe**.
- Since the workspace and Git repository are in different geographic regions, the tenant administrator must enable the setting that permits exporting Fabric items to Git repositories located in another geography.

After enabling this setting, the Fabric workspace can connect to the Azure DevOps repository despite the regional difference.

---

## Why the other options are incorrect

### ❌ Create a workspace identity

- Workspace identity provides a managed identity for the Fabric workspace.
- It is used for secure authentication to supported Azure resources.
- It does not enable Git integration or resolve geographic restrictions.

---

### ❌ Disable workspace outbound protection

- Outbound protection controls network connectivity from Fabric workloads.
- It is related to network security and external connections.
- It does not control Git repository geographic restrictions.

---

### ❌ Update the workspace region to match the repository region

- Fabric workspaces cannot simply be moved to another Azure region to match a Git repository.
- The correct solution is to enable the tenant setting that allows cross-geo Git repository connections.

---

## Key Exam Tip

For Microsoft Fabric Git integration:

| Scenario | Solution |
|---|---|
| Workspace and Git repository are in the same geography | Connect directly |
| Workspace and Git repository are in different geographies | Enable cross-geo Git export tenant setting |
| Need authentication to Azure resources | Workspace Identity |
| Need network controls | Outbound Networking |

When the question mentions:

- **Fabric workspace**
- **Azure DevOps Git repository**
- **different Azure regions/geographies**

Think:

✅ **Enable the tenant setting that allows exporting items to Git repositories in other geographical locations**
