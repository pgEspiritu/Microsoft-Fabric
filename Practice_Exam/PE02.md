# Question 11

## Question

You have a Fabric workspace that contains:

- A lakehouse named **SalesLH** that hosts a Delta table named **FactSales**
- A data warehouse named **SalesWH** that loads data from **SalesLH**
- A Microsoft Power BI semantic model named **SalesModel** built on **SalesWH**

**SalesModel** is shared to other workspaces and used by multiple reports.

You plan to rename a column in **SalesModel** and republish the model.

You need to identify downstream reports and workspaces that depend on **SalesModel** and might be affected.

**What should you use?**

> Select only one answer.

- data lineage view
- Dataflow Gen2
- Fabric IQ
- The SQL analytics endpoint

---

## Answer

✅ **data lineage view**

---

## Explanation

The correct answer is **data lineage view** because it shows the relationships and dependencies between Fabric items.

In this scenario, **SalesModel** is used by multiple reports and shared across workspaces. Before renaming a column, you need to identify:

- Reports that use the semantic model.
- Workspaces that contain dependent items.
- Upstream and downstream relationships.
- Potential impact of changes.

The **lineage view** in Microsoft Fabric provides a visual representation of data flow and dependencies between items, helping developers perform impact analysis before making changes.

---

## Why the other options are incorrect

### ❌ Dataflow Gen2

- Dataflow Gen2 is used for data ingestion and transformation workflows.
- It does not provide dependency tracking between semantic models, reports, and workspaces.

---

### ❌ Fabric IQ

- Fabric IQ provides capabilities related to business intelligence, ontology, and intelligent data experiences.
- It is not used for identifying dependencies between Fabric artifacts.

---

### ❌ The SQL analytics endpoint

- The SQL analytics endpoint provides SQL-based querying capabilities for lakehouse data.
- It does not show relationships between semantic models, reports, and workspaces.

---

## Key Exam Tip

For Microsoft Fabric impact analysis:

| Requirement | Feature |
|---|---|
| Find dependencies between reports, semantic models, and workspaces | ✅ Lineage view |
| Transform and ingest data | Dataflow Gen2 |
| Query lakehouse tables using SQL | SQL analytics endpoint |
| Business knowledge modeling | Fabric IQ |

When the question mentions:

- "identify downstream reports"
- "find dependencies"
- "impact of changes"
- "what will be affected"

Think:

✅ **Data lineage view**

---

# Question 12

## Question

You have a Fabric workspace that contains a semantic model and five reports that use the model.

You plan to share the semantic model with another workspace and use the model in five additional reports in the new workspace.

You need to analyze the downstream dependencies of the semantic model. The solution must minimize administrative effort.

From the workspace, you open the semantic model.

**What should you do next?**

> Select only one answer.

- Select Impact analysis.
- Select Lineage.
- Select Security.
- Select View related.

---

## Answer

✅ **Select Impact analysis.**

---

## Explanation

The correct answer is **Impact analysis** because it is specifically designed to identify **downstream dependencies** of a Fabric item before making changes or sharing it.

In this scenario, the semantic model is already used by multiple reports. Before sharing the model with another workspace and adding more reports, you need to understand:

- Which reports depend on the semantic model.
- Which downstream items may be affected by changes.
- Where the semantic model is being used.

The **Impact analysis** feature provides this information directly from the semantic model, reducing the administrative effort required to manually track dependencies.

---

## Why the other options are incorrect

### ❌ Select Lineage

- Lineage view shows the overall flow and relationships between Fabric items, including upstream and downstream connections.
- However, the question specifically asks to **analyze downstream dependencies of a semantic model** after opening the semantic model.
- **Impact analysis** is the dedicated feature for evaluating the effect of changes to an item.

---

### ❌ Select Security

- Security settings manage permissions and access control.
- They do not identify dependent reports or workspaces.

---

### ❌ Select View related

- View related shows related items associated with the current item.
- It is not designed for detailed dependency analysis or impact assessment.

---

## Key Exam Tip

Microsoft Fabric dependency tools:

| Feature | Purpose |
|---|---|
| **Impact analysis** | Identify downstream dependencies and assess the effect of changes |
| **Lineage view** | Visualize relationships and data flow between Fabric items |
| **Security** | Manage access permissions |
| **View related** | See related artifacts |

When a question mentions:

- "downstream dependencies"
- "what will be affected"
- "before changing or sharing an item"
- "minimize administrative effort"

✅ **Impact analysis**

# Question 14

## Question

You are developing a large semantic model.

You have a fact table that contains **500 million rows**. Most analytic queries will target aggregated data, but some users must still be able to view data on a detailed level.

You plan to create a **composite model** and implement **user-defined aggregations**.

**Which three storage modes should you use for each type of table? Each correct answer presents part of the solution.**

> Select all answers that apply.

- Aggregated tables should use Dual mode.
- Aggregated tables should use Import mode.
- The detailed fact table should use DirectQuery mode.
- The detailed fact table should use Import mode.
- Dimension tables should use DirectQuery mode.
- Dimension tables should use Dual mode.

---

## Answers

- ✅ Aggregated tables should use **Import mode**.
- ✅ The detailed fact table should use **DirectQuery mode**.
- ✅ Dimension tables should use **Dual mode**.

---

## Explanation

The correct combination for a **composite model with user-defined aggregations** is:

### ✅ Aggregated tables → Import mode

Aggregation tables should be stored in **Import** mode because they contain summarized data that is queried frequently.

Benefits include:

- Fast in-memory query performance.
- Reduced query load on the source database.
- Improved report responsiveness.

Power BI automatically uses the imported aggregation table whenever a query can be answered from the summarized data.

---

### ✅ Detailed fact table → DirectQuery mode

The detailed fact table contains **500 million rows**, making it impractical to import.

Using **DirectQuery** allows Power BI to retrieve detailed records directly from the source only when necessary.

This approach:

- Avoids storing massive datasets in memory.
- Enables access to detailed transactions.
- Works seamlessly with imported aggregation tables.

---

### ✅ Dimension tables → Dual mode

Dimension tables should use **Dual** storage mode.

Dual mode allows Power BI to behave as:

- **Import** when queries use imported aggregation tables.
- **DirectQuery** when queries require detailed fact data.

This minimizes unnecessary DirectQuery calls while maintaining compatibility with both storage modes.

---

## Why the other options are incorrect

### ❌ Aggregated tables should use Dual mode

- Aggregation tables are intended to provide fast, cached summaries.
- **Import** mode delivers the best performance.
- Dual mode offers no additional benefit for aggregation tables.

---

### ❌ The detailed fact table should use Import mode

- Importing **500 million rows** consumes significant memory and increases refresh time.
- DirectQuery is the recommended storage mode for very large fact tables in composite models.

---

### ❌ Dimension tables should use DirectQuery mode

- Using DirectQuery for dimension tables would generate unnecessary queries to the data source.
- **Dual** mode provides better performance by allowing Power BI to use cached dimension data whenever possible.

---

## Key Exam Tip

For **Composite Models with User-defined Aggregations**:

| Table Type | Recommended Storage Mode |
|------------|--------------------------|
| Aggregation tables | ✅ Import |
| Large detailed fact table | ✅ DirectQuery |
| Dimension tables | ✅ Dual |

**Memory shortcut:**

- **Import** → Fast summaries.
- **DirectQuery** → Massive detailed fact tables.
- **Dual** → Shared dimensions that work with both Import and DirectQuery.

This is the standard architecture recommended by Microsoft for **large semantic models with aggregations**.

# Question 15

## Question

You have a Fabric tenant that contains a workspace named **Workspace1**. Workspace1 is assigned to an **F64 Fabric capacity** and contains a warehouse.

You are working on a custom Microsoft Power BI semantic model that sources data from the warehouse tables. You apply optimization best practices to reduce the model size. You estimate that once the model is published to the Power BI service and fully loaded, it will approach **50 GB**.

**Which option should you configure to enable the semantic model to refresh in the Power BI service?**

> Select only one answer.

- Large semantic model storage format
- Parameters
- Query Scale-out
- Scheduled refresh

---

## Answer

✅ **Large semantic model storage format**

---

## Explanation

The correct answer is **Large semantic model storage format** because the semantic model is expected to grow to approximately **50 GB**, which exceeds the standard semantic model size limits.

Enabling **Large semantic model storage format** allows Power BI Premium/Fabric capacities (such as **F64**) to host and refresh semantic models significantly larger than the default limits. This feature optimizes how the model is stored and enables successful processing and refresh of very large datasets.

Since the workspace is already assigned to an **F64 Fabric capacity**, it supports large semantic models.

---

## Why the other options are incorrect

### ❌ Parameters

- Parameters are used to make data sources or queries configurable.
- They do not affect the maximum supported semantic model size or refresh capability.

---

### ❌ Query Scale-out

- Query Scale-out improves **query performance** by distributing read requests across multiple replicas.
- It does **not** enable large semantic model refreshes.

---

### ❌ Scheduled refresh

- Scheduled refresh automates when a semantic model refresh occurs.
- It does not increase the supported model size or enable refreshes for very large semantic models.

---

## Key Exam Tip

For large semantic models in Microsoft Fabric and Power BI:

| Requirement | Feature |
|---|---|
| Enable semantic models larger than the standard limit | ✅ Large semantic model storage format |
| Improve query concurrency | Query Scale-out |
| Automate refresh timing | Scheduled refresh |
| Make data sources configurable | Parameters |

When the question mentions:

- **Very large semantic model (tens of GB)**
- **F64/Premium/Fabric capacity**
- **Need to refresh successfully**

Think:

✅ **Large semantic model storage format**

# Question 16

## Question

You are designing a dimension table named **dimCustomer** that will be used to analyze historical sales data by customer zip code. The table will be joined to a table named **FactSales** on a column named **CustomerKey** to report historical sales data by customer zip code.

The sales data must be reported **based on the zip codes of customers at the time of the sale**, not their most recent zip code.

You need to design **dimCustomer** to contain a **fixed number of columns**.

**Which type of dimension should you choose for dimCustomer?**

> Select only one answer.

- Type 0 slowly changing dimension (SCD)
- Type 1 slowly changing dimension (SCD)
- Type 2 slowly changing dimension (SCD)
- Type 3 slowly changing dimension (SCD)

---

## Answer

✅ **Type 2 slowly changing dimension (SCD)**

---

## Explanation

The correct answer is **Type 2 Slowly Changing Dimension (SCD)** because it preserves the **full history** of changes by creating a **new row** whenever a tracked attribute (such as a customer's ZIP code) changes.

In this scenario:

- Sales must be reported using the customer's **ZIP code at the time of the sale**.
- Historical values must be preserved.
- The dimension must have a **fixed number of columns**.

A Type 2 SCD accomplishes this by inserting a new record for each change while keeping the same table structure (fixed columns). Each version of the customer has a different surrogate key, allowing the **FactSales** table to reference the correct historical record.

Example:

| CustomerKey | CustomerID | ZIP Code | Effective Date | Expiration Date | Current |
|-------------|------------|----------|----------------|-----------------|---------|
| 101 | C001 | 10001 | 2023-01-01 | 2024-05-31 | No |
| 205 | C001 | 90210 | 2024-06-01 | NULL | Yes |

A sale made in March 2024 joins to ZIP **10001**, while a sale made in July 2024 joins to ZIP **90210**.

---

## Why the other options are incorrect

### ❌ Type 0 SCD

- Type 0 never updates data.
- Original values are permanently retained.
- It cannot record customer ZIP code changes.

---

### ❌ Type 1 SCD

- Type 1 overwrites existing values.
- Previous ZIP codes are lost.
- Historical sales would incorrectly use the customer's latest ZIP code.

---

### ❌ Type 3 SCD

- Type 3 stores limited history by adding additional columns (for example, **Current ZIP** and **Previous ZIP**).
- It does not preserve unlimited history.
- It requires adding columns for historical values, making it unsuitable when many changes may occur.

---

## Key Exam Tip

Know the Slowly Changing Dimension (SCD) types:

| SCD Type | Behavior | History Preserved? | Columns Fixed? |
|----------|----------|--------------------|----------------|
| **Type 0** | Never changes | No changes allowed | ✅ Yes |
| **Type 1** | Overwrites old values | ❌ No | ✅ Yes |
| **Type 2** | Adds a new row for each change | ✅ Full history | ✅ Yes |
| **Type 3** | Adds new columns for previous values | ⚠️ Limited history | ❌ Requires additional history columns |

**Memory trick:**

- **Type 1** → Replace.
- **Type 2** → New Row.
- **Type 3** → New Column.

When the question says:

- **"historical reporting"**
- **"value at the time of the sale"**
- **"preserve history"**

Think:

✅ **Type 2 Slowly Changing Dimension (SCD)**

---

# Question 17

## Question

You have the following measure that you are reviewing as part of a model audit.

```DAX
RANKX(
    ALL('Product'[Product Name]),
    [Sales],
    ,
    DESC,
    Skip
)
```

You need to identify what the measure is calculating.

**Which statement accurately describes the DAX measure?**

> Select only one answer.

- ranks the product names by Sales, with the largest sales values getting the smallest (e.g. 1,2,3) ranks, and where product names that have tied values get the same rank number
- ranks the product names by Sales, with the largest values getting the smallest (e.g. 1,2,3) ranks, and when product names have tied values, then the next rank value, after a tie, is the rank value of the tie plus the count of tied values
- ranks the product names by Sales, with the smallest sales values getting the smallest (e.g. 1,2,3) ranks, and where product names that have tied values get the same rank number
- ranks the product names by Sales, with the smallest values getting the smallest (e.g. 1,2,3) ranks, and where product names that have tied values get unique rank numbers

---

## Answer

✅ **ranks the product names by Sales, with the largest values getting the smallest (e.g. 1,2,3) ranks, and when product names have tied values, then the next rank value, after a tie, is the rank value of the tie plus the count of tied values**

---

## Explanation

The DAX measure is:

```DAX
RANKX(
    ALL('Product'[Product Name]),
    [Sales],
    ,
    DESC,
    Skip
)
```

Here's what each argument does:

- **ALL('Product'[Product Name])** → Removes any filter on Product Name so that all products are ranked.
- **[Sales]** → Uses the Sales measure as the ranking value.
- **DESC** → Sorts in descending order, so the **highest sales receive Rank 1**.
- **Skip** → Uses **skip ranking** for ties.

### What does **Skip** mean?

When multiple products have the same Sales value, they receive the **same rank**. The next rank **skips** the appropriate number.

Example:

| Product | Sales | Rank |
|---------|------:|-----:|
| A | 100 | 1 |
| B | 90 | 2 |
| C | 90 | 2 |
| D | 80 | 4 |
| E | 70 | 5 |

Notice that after the tie at Rank **2**, the next rank is **4**, not **3**.

---

## Why the other options are incorrect

### ❌ Option 1

> *"...tied values get the same rank number."*

This is only partially correct.

It fails to mention the behavior of **Skip**, where the next rank skips numbers after ties.

---

### ❌ Option 3

> *"...smallest sales values getting the smallest ranks..."*

Incorrect because **DESC** ranks the **largest** sales values first.

---

### ❌ Option 4

> *"...smallest values..."* and *"...tied values get unique rank numbers."*

Incorrect for two reasons:

- **DESC** ranks largest values first.
- **Skip** does **not** assign unique ranks to ties.

---

## Key Exam Tip

The syntax of **RANKX** is:

```DAX
RANKX(<table>, <expression>, [,value], [order], [ties])
```

The important arguments are:

| Argument | Meaning |
|----------|---------|
| **ASC** | Lowest value gets Rank 1 |
| **DESC** | Highest value gets Rank 1 |
| **Skip** | Ties share the same rank, and subsequent ranks are skipped |
| **Dense** | Ties share the same rank, and the next rank is consecutive |

### Example

| Sales | Skip | Dense |
|------:|-----:|------:|
| 100 | 1 | 1 |
| 90 | 2 | 2 |
| 90 | 2 | 2 |
| 80 | 4 | 3 |
| 70 | 5 | 4 |

**Memory Trick:**

- **DESC** → Biggest value = Rank **1**
- **ASC** → Smallest value = Rank **1**
- **Skip** → **Skip** rank numbers after ties.
- **Dense** → Keep rank numbers **dense** (no gaps).

# Question 18

## Question

You have a Fabric warehouse that contains the following tables:

- Customer
- Date
- Product
- Store
- SalesTransactions

You are building a Microsoft Power BI semantic model that must support filtering and grouping by product, customer, store, and date.

You need to implement a **star schema** that improves query performance and summarizes measures by related descriptive attributes.

**Which table should you configure as the fact table?**

> Select only one answer.

- Customer
- Date
- Product
- SalesTransactions

---

## Answer

✅ **SalesTransactions**

---

## Explanation

The correct answer is **SalesTransactions** because it contains the **business events (transactions)** and the **numeric measures** that will be analyzed.

In a **star schema**:

- The **fact table** stores:
  - Transactional data
  - Numeric measures (for example, Sales Amount, Quantity, Cost)
  - Foreign keys to dimension tables

- **Dimension tables** store descriptive attributes used for filtering, grouping, and slicing the data.

In this scenario:

| Table | Role |
|--------|------|
| **SalesTransactions** | ✅ Fact table |
| Customer | Dimension |
| Product | Dimension |
| Store | Dimension |
| Date | Dimension |

The **SalesTransactions** table links to the Customer, Product, Store, and Date dimensions, enabling users to analyze sales by customer, product, store, and date.

---

## Why the other options are incorrect

### ❌ Customer

- Contains descriptive information about customers.
- Used for filtering and grouping, not for storing transactional measures.

---

### ❌ Date

- Provides calendar attributes such as Year, Month, Quarter, and Day.
- Acts as a dimension table for time-based analysis.

---

### ❌ Product

- Stores descriptive product information such as Product Name, Category, and Brand.
- Used as a dimension table.

---

## Key Exam Tip

A **star schema** consists of:

| Table Type | Purpose |
|------------|---------|
| **Fact Table** | Stores numeric measures and foreign keys |
| **Dimension Tables** | Store descriptive attributes used for filtering and grouping |

Typical examples:

| Fact Tables | Dimension Tables |
|-------------|------------------|
| Sales | Customer |
| Orders | Product |
| Inventory | Date |
| Transactions | Store |

**Memory Trick:**

- **Fact = Facts = Numbers**
- **Dimension = Description**

When the question asks:

- **"Which table is the fact table?"**
- **"Summarizes measures"**
- **"Supports filtering by customer, product, store, and date"**

Think:

✅ **SalesTransactions**

# Question 19

## Question

You have an Azure SQL database.

You have a Microsoft Power BI report connected to a semantic model that uses a **DirectQuery** connection to the database.

You need to reduce the number of queries sent to the database when a user is interacting with the report by using filters and/or slicers.

**What should you do?**

> Select only one answer.

- Add apply buttons to all the basic filters.
- Add Top N filters to all the visuals.
- Change default visual interaction from cross highlighting to cross filtering.
- Enable automatic page refresh for each report page.

---

## Answer

✅ **Add apply buttons to all the basic filters.**

---

## Explanation

The correct answer is **Add apply buttons to all the basic filters** because it reduces the number of queries sent to the Azure SQL database when users interact with a DirectQuery report.

With DirectQuery:

- Every interaction that changes a filter or slicer can trigger a query back to the source database.
- Without an Apply button, each filter selection may immediately send a query.
- With Apply buttons enabled, users can make multiple filter selections and submit them together, causing Power BI to send fewer queries.

This reduces unnecessary database workload and improves report performance.

---

## Why the other options are incorrect

### ❌ Add Top N filters to all the visuals

- Top N filters limit the number of displayed results.
- They do not reduce the number of queries generated when users interact with filters or slicers.

---

### ❌ Change default visual interaction from cross highlighting to cross filtering

- Cross filtering can affect the data displayed in other visuals.
- However, changing interaction behavior does not directly reduce the number of queries triggered by slicer and filter changes.

---

### ❌ Enable automatic page refresh for each report page

- Automatic page refresh is used for near real-time monitoring scenarios.
- It increases query frequency rather than reducing queries.

---

## Key Exam Tip

For Power BI **DirectQuery performance optimization**:

| Requirement | Feature |
|---|---|
| Reduce queries caused by slicer/filter changes | ✅ Apply buttons |
| Reduce data displayed | Top N filters |
| Change visual behavior | Cross filtering/highlighting |
| Refresh data automatically | Automatic page refresh |

When the question mentions:

- **DirectQuery**
- **too many queries**
- **users interacting with filters/slicers**

Think:

✅ **Add Apply buttons to filters**

# Question 20

## Question

You have a Microsoft Power BI report page that takes longer than expected to display all its visuals.

You need to identify which report element consumes most of the rendering time. The solution must minimize administrative effort and how long it takes to capture the rendering information of each element on the report page.

**What should you use?**

> Select only one answer.

- DAX Studio
- Performance analyzer
- SQL Server Profiler
- Tabular Editor

---

## Answer

✅ **Performance analyzer**

---

## Explanation

The correct answer is **Performance analyzer** because it is a built-in Power BI Desktop feature designed to identify which report elements are consuming the most rendering time.

Performance analyzer captures the time taken by each visual to load, including:

- DAX query execution time.
- Visual display/rendering time.
- Other processing time.

It allows you to quickly identify slow visuals and determine which report elements need optimization.

Using Performance analyzer requires minimal administrative effort because it is available directly within Power BI Desktop and does not require external tools or additional configuration.

---

## Why the other options are incorrect

### ❌ DAX Studio

- DAX Studio is an external tool used for advanced DAX query analysis and performance tuning.
- It can analyze query execution details but does not directly identify which report visual consumes the most rendering time.

---

### ❌ SQL Server Profiler

- SQL Server Profiler can trace database queries and events.
- It is mainly used for SQL Server and Analysis Services monitoring.
- It requires additional configuration and is not the simplest way to analyze Power BI visual rendering performance.

---

### ❌ Tabular Editor

- Tabular Editor is used for semantic model development and advanced model management.
- It does not measure report visual rendering performance.

---

## Key Exam Tip

For Power BI performance troubleshooting:

| Requirement | Tool |
|---|---|
| Identify slow visuals on a report page | ✅ Performance analyzer |
| Analyze DAX query performance | DAX Studio |
| Trace Analysis Services queries | SQL Server Profiler |
| Edit/manage semantic models | Tabular Editor |

When the question mentions:

- **report page is slow**
- **identify which visual takes the most time**
- **capture rendering information**
- **minimize effort**

Think:

✅ **Performance analyzer**
