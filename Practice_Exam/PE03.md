# Question 21

## Question

You have a Fabric tenant that contains a lakehouse named **Lakehouse1**.

You have an external Snowflake database that contains a table with **200 million rows**.

You need to use a data pipeline to migrate the database to **Lakehouse1**.

**What is the most performant (fastest) method for ingesting data this large (200 million rows) by using a data pipeline?**

> Select only one answer.

- Data Pipeline (Copy data)
- Data Pipeline (Dataflow Gen2)
- Data Pipeline (Lookup)
- Data Pipeline Spark (Notebook)

---

## Answer

✅ **Data Pipeline (Copy data)**

---

## Explanation

The correct answer is **Data Pipeline (Copy data)** because the Copy activity in Microsoft Fabric Data Pipelines is optimized for **large-scale data movement** between data sources and destinations.

For migrating a **200 million-row Snowflake table** to a Fabric Lakehouse, Copy data provides:

- High-throughput data transfer.
- Parallel data ingestion.
- Optimized source-to-target movement.
- Minimal transformation overhead.

Since the goal is to **migrate a large dataset**, the fastest and most efficient approach is to use the native **Copy data** activity.

---

## Why the other options are incorrect

### ❌ Data Pipeline (Dataflow Gen2)

- Dataflow Gen2 is designed for data preparation and transformation using Power Query.
- It introduces additional transformation processing overhead.
- It is not the optimal choice for moving hundreds of millions of rows.

---

### ❌ Data Pipeline (Lookup)

- Lookup activities are used to retrieve metadata or small amounts of data for pipeline control logic.
- They are not designed for bulk data ingestion.

---

### ❌ Data Pipeline Spark (Notebook)

- Spark notebooks can process large datasets and perform complex transformations.
- However, for simple migration without significant transformation, Spark introduces unnecessary processing overhead.
- Copy activity is optimized specifically for high-volume data movement.

---

## Key Exam Tip

For Microsoft Fabric data ingestion:

| Requirement | Recommended Tool |
|---|---|
| Move very large datasets quickly | ✅ Copy data activity |
| Transform/clean data | Dataflow Gen2 |
| Pipeline control lookups | Lookup activity |
| Complex big data processing | Spark Notebook |

When the question mentions:

- **Large table (millions/billions of rows)**
- **Migration**
- **Fastest ingestion**
- **Source-to-target copy**

Think:

✅ **Data Pipeline (Copy data)**

---

# Question 22

## Question

You have a Fabric tenant that contains a lakehouse named **Lakehouse1**.

A **SELECT** query from a managed Delta table in **Lakehouse1** takes longer than expected to complete. The table receives new records daily and must keep change history for **seven days**.

You notice that the table contains **1,000 Parquet files** that are each **1 MB**.

You need to improve query performance and reduce storage costs.

**What should you do from Lakehouse explorer?**

> Select only one answer.

- Manually delete any files that have a creation date that is older than seven days.
- Select Maintenance and run the OPTIMIZE command.
- Select Maintenance and run the OPTIMIZE command as well as the VACUUM command with a retention policy of seven days.
- Select Maintenance and run the VACUUM command with a retention policy of seven days.

---

## Answer

✅ **Select Maintenance and run the OPTIMIZE command as well as the VACUUM command with a retention policy of seven days.**

---

## Explanation

The correct answer is to run both **OPTIMIZE** and **VACUUM** because the table has two separate problems:

1. **Poor query performance due to many small files**
2. **Increased storage usage due to obsolete files**

### ✅ OPTIMIZE

The table contains **1,000 small Parquet files (1 MB each)**.

Small files increase query overhead because the query engine must open and process many files. The **OPTIMIZE** command:

- Compacts small Parquet files into larger files.
- Reduces file count.
- Improves Delta table read performance.

### ✅ VACUUM with a seven-day retention policy

Delta tables maintain old file versions to support:

- Time travel.
- Change history.
- Recovery.

Since the table must keep history for **seven days**, running **VACUUM with a seven-day retention period** removes obsolete files older than seven days while preserving the required history.

Together:

- **OPTIMIZE** → Improves performance.
- **VACUUM (7 days)** → Reduces storage costs while keeping required history.

---

## Why the other options are incorrect

### ❌ Manually delete any files that have a creation date older than seven days

- Manual deletion is not recommended for Delta tables.
- It can break Delta transaction logs and table consistency.
- Delta maintenance operations should manage files.

---

### ❌ Select Maintenance and run the OPTIMIZE command

- OPTIMIZE improves performance by compacting files.
- However, it does not remove obsolete files created by previous table changes.
- Storage costs would not be reduced.

---

### ❌ Select Maintenance and run the VACUUM command with a retention policy of seven days

- VACUUM removes old unused files and reduces storage.
- However, it does not compact the 1,000 small files.
- Query performance would remain affected.

---

## Key Exam Tip

For Microsoft Fabric Lakehouse Delta table maintenance:

| Problem | Solution |
|---|---|
| Too many small files | ✅ OPTIMIZE |
| Old unused files consuming storage | ✅ VACUUM |
| Need both performance + storage improvement | ✅ OPTIMIZE + VACUUM |

When a question mentions:

- Many small Parquet files
- Slow SELECT queries
- Delta table history retention
- Reduce storage costs

Think:

✅ **OPTIMIZE + VACUUM with the required retention period**

---

# Question 23

## Question

You are managing a set of **Dataflow Gen2 queries** that are currently ingesting tables into a **Fabric lakehouse**.

You need to ensure that the tables are optimized for **Direct Lake connections** that will be used by connected semantic models.

**What should you do?**

> Select only one answer.

- Apply an incremental refresh policy to the semantic model refreshes.
- Run the VACUUM command.
- Use OPTIMIZE to apply V-Order.
- Use shortcuts to the lakehouse tables from the semantic models.

---

## Answer

✅ **Use OPTIMIZE to apply V-Order.**

---

## Explanation

The correct answer is **Use OPTIMIZE to apply V-Order** because **V-Order optimization improves the performance of Direct Lake queries** against Delta tables in Microsoft Fabric.

When Dataflow Gen2 loads data into a Fabric lakehouse, the resulting Delta tables can be optimized by applying **V-Order**, which:

- Improves Parquet file layout.
- Optimizes compression.
- Improves scan efficiency.
- Enhances query performance for Direct Lake semantic models.

Since Direct Lake reads data directly from OneLake without importing it into the semantic model, optimizing the underlying Delta tables is important for performance.

The **OPTIMIZE** command in Fabric can apply V-Order optimization to Delta tables.

---

## Why the other options are incorrect

### ❌ Apply an incremental refresh policy to the semantic model refreshes

- Incremental refresh is used for Import mode semantic models.
- Direct Lake semantic models do not rely on traditional refresh operations.
- It does not optimize the underlying lakehouse tables.

---

### ❌ Run the VACUUM command

- VACUUM removes old unused Delta files.
- It helps reduce storage consumption.
- It does not improve the physical layout or query performance of Direct Lake tables.

---

### ❌ Use shortcuts to the lakehouse tables from the semantic models

- Shortcuts provide access to data stored in other locations.
- They do not optimize Delta table storage or improve Direct Lake query performance.

---

## Key Exam Tip

For Microsoft Fabric Lakehouse optimization:

| Requirement | Feature |
|---|---|
| Improve Direct Lake performance | ✅ OPTIMIZE with V-Order |
| Remove obsolete Delta files | VACUUM |
| Reduce import model refresh time | Incremental refresh |
| Access external data without copying | Shortcuts |

When the question mentions:

- **Direct Lake**
- **Lakehouse Delta tables**
- **Semantic model performance**
- **Optimize tables**

Think:

✅ **OPTIMIZE to apply V-Order**

# Question 24

## Question

You have a Fabric tenant that contains a workspace named **Workspace1**. Workspace1 contains a lakehouse named **Lakehouse1**.

You open a notebook in **Lakehouse1** and attach it to a Spark session.

You plan to start a new notebook in **Lakehouse1** and attach it to the same Spark session. However, you notice that the **New high concurrency session** option is unavailable, and the only available option is **Standard session**.

You need to ensure that the high concurrency mode for notebooks is enabled.

**Where can you check the high concurrency mode?**

> Select only one answer.

- Fabric tenant settings
- Lakehouse settings
- Notebook properties from the Edit menu
- Workspace settings

---

## Answer

✅ **Workspace settings**

---

## Explanation

The correct answer is **Workspace settings** because **Spark high concurrency mode is configured at the workspace level** in Microsoft Fabric.

High concurrency mode allows multiple notebooks to share the same Spark session, which can improve resource utilization and reduce startup overhead when multiple notebooks run together.

To verify or enable the setting:

1. Open the Fabric workspace.
2. Go to **Workspace settings**.
3. Navigate to the **Spark settings** section.
4. Check whether **high concurrency mode for notebooks** is enabled.

Once enabled, notebooks in that workspace can use the **New high concurrency session** option when attaching to Spark sessions.

---

## Why the other options are incorrect

### ❌ Fabric tenant settings

- Tenant settings control organization-wide Fabric features and permissions.
- Spark session behavior, including notebook high concurrency mode, is configured at the workspace level.

---

### ❌ Lakehouse settings

- Lakehouse settings manage lakehouse-specific configurations.
- Spark session settings are not controlled by individual lakehouses.

---

### ❌ Notebook properties from the Edit menu

- Notebook properties control notebook-specific settings.
- High concurrency availability is not configured at the individual notebook level.

---

## Key Exam Tip

Microsoft Fabric Spark configuration levels:

| Setting | Location |
|---|---|
| Enable high concurrency sessions | ✅ Workspace settings |
| Manage organization-wide Fabric features | Tenant settings |
| Configure lakehouse resources | Lakehouse settings |
| Notebook-specific options | Notebook settings/properties |

When a question mentions:

- **New high concurrency session unavailable**
- **Multiple notebooks sharing a Spark session**
- **Spark session configuration**

Think:

✅ **Workspace settings**

# Question 25

## Question

You have a Fabric warehouse named **Warehouse1**.

You discover a SQL query that performs poorly, and you notice that table statistics are out of date.

You need to manually update the statistics to improve query performance for the table.

**Which column statistics should you update?**

> Select only one answer.

- columns of the VARCHAR and NVARCHAR data type
- columns used in GROUP BY clauses
- columns with high cardinality
- primary key columns

---

## Answer

✅ **columns with high cardinality**

---

## Explanation

The correct answer is **columns with high cardinality** because statistics on high-cardinality columns provide the query optimizer with more accurate information about data distribution.

In Microsoft Fabric Warehouse, the query optimizer uses statistics to estimate:

- The number of rows returned by a query.
- The most efficient execution plan.
- Which indexes or data access strategies to use.

High-cardinality columns contain many unique values, such as:

- Customer IDs
- Transaction IDs
- Product keys
- Dates with high granularity

Accurate statistics on these columns help the optimizer make better decisions, especially for filtering, joins, and query execution plans.

---

## Why the other options are incorrect

### ❌ Columns of the VARCHAR and NVARCHAR data type

- Data type alone does not determine whether statistics are important.
- A VARCHAR/NVARCHAR column may have low or high cardinality depending on the data.

---

### ❌ Columns used in GROUP BY clauses

- Columns used in GROUP BY operations may benefit from statistics, but they are not the primary target for manual statistics updates.
- Cardinality and data distribution are more important factors.

---

### ❌ Primary key columns

- Primary keys often have unique values and may already have useful statistics.
- The reason to update statistics is not simply because a column is a primary key, but because the statistics are stale and inaccurate, especially for columns with high data variability.

---

## Key Exam Tip

For SQL performance tuning:

| Column characteristic | Importance for statistics |
|---|---|
| High cardinality | ✅ High priority |
| Frequently filtered/joined columns | Important |
| Primary keys | Usually already optimized |
| Data type alone | Not enough reason |

When the question mentions:

- Poor query performance
- Out-of-date statistics
- Manual statistics updates

Think:

✅ **Update statistics on high-cardinality columns**

---

# Question 26

## Question

You have a DAX measure that contains the following code.

```DAX
Variance KPI =

IF(
    [Variance] > 0.80,
    "Amazing!",
    IF(
        [Variance] > 0.60,
        "Good",
        "Bad"
    )
)
```

You need to optimize the measure so that it will calculate faster.

**Which code should you use?**

> Select only one answer.

- 
```DAX
SWITCH(
    TRUE(),
    [Variance] > 0.80, "Amazing!",
    [Variance] > 0.60, "Good",
    "Bad"
)
```

- 
```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    Calc > 0.80, "Amazing!",
    Calc > 0.60, "Good",
    "Bad"
)
```

- 
```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    Calc > 0.80, "Amazing!",
    [Variance] > 0.60, "Good",
    "Bad"
)
```

- 
```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    [Variance] > 0.80, "Amazing!",
    [Variance] > 0.60, "Good",
    "Bad"
)
```

---

## Answer

✅ **Option 2**

```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    Calc > 0.80, "Amazing!",
    Calc > 0.60, "Good",
    "Bad"
)
```

---

## Explanation

The optimized solution stores the result of **[Variance]** in a variable and then reuses the variable in the `SWITCH` expression.

### Original measure

```DAX
IF(
    [Variance] > 0.80,
    "Amazing!",
    IF(
        [Variance] > 0.60,
        "Good",
        "Bad"
    )
)
```

The measure evaluates `[Variance]` multiple times:

1. Check if `[Variance] > 0.80`
2. Check if `[Variance] > 0.60`

If `[Variance]` is a complex calculation, repeating the evaluation can increase query execution time.

### Optimized version

```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    Calc > 0.80, "Amazing!",
    Calc > 0.60, "Good",
    "Bad"
)
```

The variable stores the calculation result once and reuses it, reducing repeated evaluation and improving performance.

---

## Why the other options are incorrect

### ❌ Option 1

```DAX
SWITCH(
    TRUE(),
    [Variance] > 0.80, "Amazing!",
    [Variance] > 0.60, "Good",
    "Bad"
)
```

- This improves readability by replacing nested `IF` statements.
- However, `[Variance]` is still evaluated multiple times.
- It does not provide the performance optimization required.

---

### ❌ Option 3

```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    Calc > 0.80, "Amazing!",
    [Variance] > 0.60, "Good",
    "Bad"
)
```

- The first condition uses the variable.
- The second condition recalculates `[Variance]`.
- It does not fully optimize the measure.

---

### ❌ Option 4

```DAX
VAR Calc = [Variance]

RETURN

SWITCH(
    TRUE(),
    [Variance] > 0.80, "Amazing!",
    [Variance] > 0.60, "Good",
    "Bad"
)
```

- The variable is created but never used.
- `[Variance]` is still evaluated repeatedly.
- This provides no performance improvement.

---

## Key Exam Tip

For DAX performance optimization:

Use variables (`VAR`) when:

- A measure is referenced multiple times.
- A calculation is expensive.
- You want to improve readability and avoid repeated evaluation.

Example:

❌ Less efficient:

```DAX
IF([Sales] > 1000, [Sales] * 0.1, [Sales] * 0.05)
```

✅ Better:

```DAX
VAR TotalSales = [Sales]

RETURN
IF(TotalSales > 1000, TotalSales * 0.1, TotalSales * 0.05)
```

**Memory trick:**

Repeated calculation → Store in `VAR` → Reuse variable.

---

## Answer

✅ **Dataflows Gen2**

---

Dataflows Gen2 uses the **Power Query** engine, allowing users to:

- Connect to multiple data sources.
- Perform data cleansing and transformation steps.
- Apply custom transformations using a graphical interface.
