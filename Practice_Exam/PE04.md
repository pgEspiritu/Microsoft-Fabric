# Question 31

## Question

You have a Fabric tenant that contains a warehouse named **Warehouse1**.

You have a large **1 TB dataset** in an external data source.

You need to recommend a method to ingest the dataset into **Warehouse1**.

The solution must provide:

- The **highest throughput**
- A **low-code/no-code development model**

**What should you recommend?**

> Select only one answer.

- Copy data activity
- Dataflow Gen2
- Spark notebook
- Shortcut

---

## Answer

✅ **Copy data activity**

---

## Explanation

The correct answer is **Copy data activity** because it is designed for **high-performance data ingestion and movement at scale** while requiring minimal coding.

For a **1 TB dataset**, Copy data activity provides:

- High-throughput bulk data transfer.
- Parallel data movement.
- Native connectors to many external data sources.
- Low-code/no-code configuration through Fabric Data Pipelines.
- Efficient loading into a Fabric Warehouse.

Since the requirement is primarily to **move a very large amount of data** into Warehouse1, the Copy data activity is the best choice.

---

## Why the other options are incorrect

### ❌ Dataflow Gen2

- Dataflow Gen2 provides a low-code/no-code experience.
- However, it is primarily designed for data transformation and preparation.
- It is not optimized for maximum throughput when ingesting very large datasets such as 1 TB.

---

### ❌ Spark notebook

- Spark notebooks can process very large datasets.
- However, they require coding skills (PySpark, SQL, Scala).
- They require more development effort and are not the lowest administrative effort option.

---

### ❌ Shortcut

- Shortcuts provide virtual access to data stored in another location without copying it.
- They do not ingest data into Warehouse1.
- They are not a data loading method.

---

## Key Exam Tip

For Microsoft Fabric ingestion:

| Requirement | Recommended Feature |
|---|---|
| Highest throughput bulk ingestion | ✅ Copy data activity |
| Low-code transformations | Dataflow Gen2 |
| Complex big data processing | Spark notebook |
| Access external data without copying | Shortcut |

When the question mentions:

- **Very large dataset (TB scale)**
- **Ingest/load data**
- **Highest throughput**
- **Low-code/no-code**

Think:

✅ **Copy data activity**

---

# Question 32

## Question

You have an Azure SQL database that contains a fact table named **UnpostedSales**. UnpostedSales contains **unposted payments**.

Each day, payment records from the previous day are automatically **truncated** from the UnpostedSales table and replaced with today's payment records.

You need to use a **Dataflow Gen2 query** to import the data into either a **lakehouse or a warehouse**.

The solution must ensure that **all current and historical records are maintained**.

**What should you do to retain current and historical records during a refresh?**

> Select only one answer.

- Configure the refresh to append data for the query.
- Configure the refresh to replace data for the query.
- Use Optimize to apply V-order for the query.
- Ensure that query folding occurs for the whole query.

---

## Answer

✅ **Configure the refresh to append data for the query.**

---

## Explanation

The correct answer is **Configure the refresh to append data for the query** because the source table (**UnpostedSales**) only contains the current day's records.

Each day:

1. Previous records are removed from the source table.
2. New payment records are loaded.
3. The source no longer contains historical data.

If the Dataflow Gen2 refresh uses **replace**, the destination table would also be overwritten, causing historical records to be lost.

By configuring the query to **append**:

- New daily payment records are added to the destination.
- Existing historical records remain available.
- The lakehouse or warehouse maintains a complete history of payments.

---

## Why the other options are incorrect

### ❌ Configure the refresh to replace data for the query

- Replace refresh deletes existing destination data and loads only the latest source data.
- Since the source table is truncated daily, historical records would be lost.

---

### ❌ Use Optimize to apply V-order for the query

- V-Order optimization improves Delta table storage layout and query performance.
- It does not preserve historical records during ingestion.

---

### ❌ Ensure that query folding occurs for the whole query

- Query folding improves transformation performance by pushing operations back to the source.
- It does not maintain historical records.

---

## Key Exam Tip

For Dataflow Gen2 refresh behavior:

| Refresh Mode | Behavior |
|---|---|
| **Append** | Adds new records and keeps existing history |
| **Replace** | Deletes existing data and reloads current data |

When the question mentions:

- Source table is truncated or refreshed daily
- Need to preserve historical records
- Need incremental history accumulation

Think:

✅ **Append data**

---

You have a Fabric lakehouse that contains a managed Delta table named **Product**.

```python
df = spark.sql("SELECT * FROM Product")
```

> Select only one answer.

- `describe(df.limit(100))`
- `df.describe(100)`
- `df.printSchema(100)`
- `display(df.limit(100))`

---

## Answer

✅ **`display(df.limit(100))`**

---

## Explanation

The correct answer is:

```python
display(df.limit(100))
```

because the `display()` function in Microsoft Fabric notebooks is used to render DataFrame results in a readable table format.

The `limit()` function restricts the DataFrame output to the first **100 rows**.

Example:

```python
df.limit(100)
```

returns a DataFrame containing only 100 records.

Then:

```python
display(df.limit(100))
```

displays those records in the notebook output.

This is the standard approach in Fabric notebooks when you want to visually inspect a sample of data.

---

## Why the other options are incorrect

### ❌ `describe(df.limit(100))`

- `describe()` is not a standalone function for displaying rows.
- DataFrame `describe()` provides statistical summaries such as:
  - count
  - mean
  - standard deviation
  - minimum
  - maximum

Example:

```python
df.describe()
```

It does not display the first 100 records.

---

### ❌ `df.describe(100)`

- The `describe()` method does not accept a row limit parameter.
- It generates summary statistics, not table output.

---

### ❌ `df.printSchema(100)`

- `printSchema()` displays the DataFrame structure:
  - column names
  - data types
  - hierarchy

Example:

```python
df.printSchema()
```

- It does not display data rows and does not accept a row count argument.

---

## Key Exam Tip

# Question 36

## Question

You are designing a semantic model for a Microsoft Power BI report.

You have a table named **Employee** that contains the following columns:

- EmployeeID
- EmployeeName
- EmployeePosition

You have a table named **Contract** that contains the following columns:

- EmployeeID
- ContractType

You plan to denormalize both tables and include the **ContractType** attribute.

You need to ensure that **all the rows in the Employee table are preserved** and include any matching rows from the Contract table.

**Which type of join should you specify in the Power Query Merge queries transformation?**

> Select only one answer.

- cross
- inner
- Left outer
- Left Anti Join

---

## Answer

✅ **Left outer**

---

## Explanation

The correct answer is **Left outer** because a **Left Outer Join** preserves **all rows from the left table** and includes matching rows from the right table.

In this scenario:

- **Employee** is the table that must be preserved.
- **Contract** provides the additional attribute (**ContractType**).
- The merge should keep every employee, even if they do not have a matching contract record.

The result will contain:

- All employees from the Employee table.
- ContractType values where a matching EmployeeID exists in the Contract table.
- Blank/null ContractType values for employees without contracts.

Example:

### Employee

| EmployeeID | EmployeeName |
|---|---|
| 1 | John |
| 2 | Mary |
| 3 | Alex |

### Contract

| EmployeeID | ContractType |
|---|---|
| 1 | Full-Time |
| 2 | Part-Time |

### Left Outer Join Result

| EmployeeID | EmployeeName | ContractType |
|---|---|---|
| 1 | John | Full-Time |
| 2 | Mary | Part-Time |
| 3 | Alex | null |

---

## Why the other options are incorrect

### ❌ Cross

- A cross join creates every possible combination of rows between both tables.
- It does not match records based on EmployeeID.

---

### ❌ Inner

- An inner join returns only rows where matching EmployeeID values exist in both tables.
- Employees without contracts would be removed.

---

### ❌ Left Anti Join

- A left anti join returns only rows from the left table that **do not have matches** in the right table.
- It is used to find missing relationships, not to combine attributes.

---

## Key Exam Tip

Power Query Merge join types:

| Join Type | Result |
|---|---|
| **Left Outer** | Keep all rows from first table + matching rows from second |
| Inner | Only matching rows |
| Right Outer | Keep all rows from second table + matching rows from first |
| Full Outer | Keep all rows from both tables |
| Left Anti | Rows only in first table without matches |
| Cross | Every possible combination |

When the question says:

- "preserve all rows from the first table"
- "include matching data from another table"

Think:

✅ **Left Outer Join**

- It does not calculate values or create derived columns.

# Question 38

## Question

You have a **Fabric warehouse**.

You have an **Azure SQL database** that contains:

- A fact table named **Sales**
- A second table named **ExceptionRecords**

Both tables contain a unique key column named **Record ID**.

You plan to ingest the **Sales** table into the warehouse.

You need to use **Dataflow Gen2** to configure a merge type to ensure that:

- The **Sales** table excludes any records found in the **ExceptionRecords** table.
- **Query folding is maintained.**

**Which applied steps should you use?**

> Select only one answer.

- Merge (inner join) applied step, and then the expand columns applied step
- Merge (left anti join) applied step, and then the expand columns applied step
- Merge (left anti join) applied step, delete the “expand columns” column
- Merge (right anti join) applied step, and then the expand columns applied step

---

## Answer

✅ **Merge (left anti join) applied step, delete the “expand columns” column**

---

## Explanation

The correct answer is:

✅ **Merge (left anti join) applied step, delete the “expand columns” column**

A **Left Anti Join** returns only the rows from the first (left) table that **do not have matching records** in the second (right) table.

In this scenario:

- **Left table:** Sales
- **Right table:** ExceptionRecords
- Join key: Record ID

The requirement is to keep only Sales records that are **not present** in ExceptionRecords.

A Left Anti Join produces exactly that result:

```
Sales - ExceptionRecords = Valid Sales Records
```

---

### Why delete the "expand columns" step?

In Power Query/Dataflow Gen2:

- A merge operation normally creates a nested table column containing matching rows.
- For anti joins, the purpose is only to filter out matching records.
- Expanding columns is unnecessary because no columns from ExceptionRecords are needed.

Removing the expand step also helps maintain **query folding** back to Azure SQL.

The SQL source can translate the operation efficiently into a database-side filtering operation.

---

## Why the other options are incorrect

### ❌ Merge (inner join) applied step, and then the expand columns applied step

- An inner join returns only records that exist in both tables.
- This would keep exception records instead of removing them.
- It does not satisfy the requirement.

---

### ❌ Merge (left anti join) applied step, and then the expand columns applied step

- The join type is correct.
- However, expanding columns is unnecessary for a Left Anti Join.
- Adding the expand step can prevent efficient query folding.

---

### ❌ Merge (right anti join) applied step, and then the expand columns applied step

- A right anti join returns records that exist only in the right table.
- It would return records from ExceptionRecords that are missing from Sales.
- This is the opposite of the required result.

---

## Key Exam Tip

Power Query Merge joins:

| Join Type | Purpose |
|---|---|
| Inner | Keep matching rows |
| Left Outer | Keep all left rows + matches |
| Left Anti | ✅ Keep left rows without matches |
| Right Anti | Keep right rows without matches |
| Full Outer | Keep all rows from both tables |

When the requirement says:

- "Exclude records found in another table"
- "Remove matching records"
- "Keep only records not in exceptions"

Think:

✅ **Left Anti Join + remove expand step**

# Question 40

## Question

You have a Fabric tenant that contains a **lakehouse**.

You plan to use a **Fabric notebook and PySpark** to read sales data and save the data as a **Delta table** named **Sales**.

The table must be partitioned by:

- Sales Year
- Quarter

You load the sales data to a DataFrame named **df** that contains a **Year** column and a **Quarter** column.

**Which command should you run next?**

> Select only one answer.

- `df.write.mode("overwrite").format("delta").partitionBy("Year",Quarter").save("Files/Sales")`

- `df.write.mode("overwrite").format("delta").partitionBy("Year","Quarter").save("Tables/Sales")`

- `df.write.mode("overwrite").format("parquet").partitionBy("Year","Quarter").save("Files/Sales")`

- `df.write.mode("overwrite").format("parquet").partitionBy("Year","Quarter").save("Tables/Sales")`

---

# Answer

✅ **Option 2**

```python
df.write.mode("overwrite").format("delta").partitionBy("Year","Quarter").save("Tables/Sales")
```

---

# Explanation

The correct answer is **Option 2** because the requirement is to create a **Delta table** named **Sales** in the Fabric lakehouse.

In Microsoft Fabric lakehouses:

- **Tables/** stores managed tables that can be queried using SQL analytics endpoint and used by other Fabric workloads.
- **Files/** stores unmanaged files that are not automatically registered as tables.

The command:

```python
df.write.mode("overwrite") \
  .format("delta") \
  .partitionBy("Year","Quarter") \
  .save("Tables/Sales")
```

does the following:

### `format("delta")`

Creates the data using the Delta Lake format required for lakehouse tables.

### `partitionBy("Year","Quarter")`

Partitions the table based on:

- Sales Year
- Quarter

This improves query performance when filtering by these columns.

### `save("Tables/Sales")`

Writes the data as a managed lakehouse table named **Sales**.

---

# Why the other options are incorrect

## ❌ Option 1

```python
df.write.mode("overwrite").format("delta").partitionBy("Year",Quarter").save("Files/Sales")
```

Problems:

- The syntax is incorrect because `Quarter` is missing quotation marks.
- The Files folder is not used for managed lakehouse tables.

---

## ❌ Option 3

```python
df.write.mode("overwrite").format("parquet").partitionBy("Year","Quarter").save("Files/Sales")
```

Problems:

- Parquet is not Delta format.
- Files/ does not create a managed lakehouse table.
- The requirement is to create a Delta table.

## ❌ Option 4

```python
df.write.mode("overwrite").format("parquet").partitionBy("Year","Quarter").save("Tables/Sales")
```

Problems:

- Uses Parquet instead of Delta.
- Fabric lakehouse managed tables require Delta format.

# Key Exam Tip

Fabric Lakehouse storage:

| Location | Purpose |
|---|---|
| `Tables/` | ✅ Managed Delta tables |
| `Files/` | Raw files and unmanaged data |

PySpark table creation pattern:

```python
df.write \
  .format("delta") \
  .partitionBy("Column1","Column2") \
  .save("Tables/TableName")
```

When the question mentions:

- Create a Delta table
- Use lakehouse table storage
- Partition by columns

Think:

✅ **format("delta") + partitionBy() + save("Tables/TableName")**
