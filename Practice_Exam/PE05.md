# Question 41

## Question

You have a Fabric workspace. The workspace contains a **Dataflow Gen2** query that displays dimensional product information.

The query table contains a column named **Product ID/Name** that is a concatenation of **Product ID** and **Product Name** values.

You need to use an applied step in **Microsoft Power Query Editor** to create a new column for:

- Product ID
- Product Name

The solution must use a **single command** to create two new columns and remove the original combined (**Product ID/Name**) column.

**Which applied step should you use?**

> Select only one answer.

- Add Column From Example
- Conditional Column
- Replace Values
- Split Column

---

# Answer

✅ **Split Column**

---

# Explanation

The correct answer is **Split Column** because it is designed to separate a single column containing combined values into multiple columns.

In this scenario:

- Original column:

```
Product ID/Name
```

contains concatenated values.

Example:

| Product ID/Name |
|---|
| 1001/Laptop |
| 1002/Monitor |

Using **Split Column**, Power Query can split the values into:

| Product ID | Product Name |
|---|---|
| 1001 | Laptop |
| 1002 | Monitor |

The Split Column transformation can:

- Create multiple columns from one column.
- Remove the original combined column during the operation.
- Be completed as a single applied step.

---

# Why the other options are incorrect

## ❌ Add Column From Example

- Creates a new column by detecting patterns from sample values.
- It does not directly split an existing column into multiple columns and remove the original column.

---

## ❌ Conditional Column

- Creates a new column based on logical conditions.
- It is used for rules such as:

```
If Sales > 1000 then "High" else "Low"
```

- It does not split text values.

---

## ❌ Replace Values

- Used to find and replace existing values.
- It does not create multiple columns.

---

# Key Exam Tip

Power Query transformations:

| Requirement | Transformation |
|---|---|
| Separate one column into multiple columns | ✅ Split Column |
| Create values based on conditions | Conditional Column |
| Replace text/value patterns | Replace Values |
| Generate column using examples | Add Column From Example |

When the question mentions:

- Concatenated column
- Need multiple columns
- Remove original combined column

Think:

✅ **Split Column**

---

# Question 42

## Question

You have a Fabric workspace that contains a **Microsoft Power BI report**.

You need to modify the **column names in the Power BI report** without changing the original names in the underlying **Delta table**.

**Which warehouse object should you create?**

> Select only one answer.

- columnstore index
- schema
- table-valued function
- view

---

# Answer

✅ **view**

---

# Explanation

The correct answer is **view** because a **view** allows you to present data with different column names without modifying the underlying table.

In this scenario:

- The original Delta table column names must remain unchanged.
- The Power BI report requires different column names.
- A view can rename columns using aliases.

Example:

Original Delta table:

| Customer_ID | Sales_Amount |
|---|---:|
| 101 | 500 |

Create a view:

```sql
CREATE VIEW SalesView AS
SELECT
    Customer_ID AS CustomerID,
    Sales_Amount AS TotalSales
FROM Sales;
```

Power BI connects to the view and displays:

| CustomerID | TotalSales |
|---|---:|
| 101 | 500 |

The underlying Delta table remains unchanged.

---

# Why the other options are incorrect

## ❌ Columnstore index

- A columnstore index improves query performance by optimizing storage and retrieval.
- It does not change column names or provide a renamed data layer.

---

## ❌ Schema

- A schema organizes database objects such as tables and views.
- It does not rename columns in an existing table for reporting purposes.

---

## ❌ Table-valued function

- A table-valued function returns a table result based on logic or parameters.
- Although it can transform data, it is not the recommended object for simply exposing renamed columns.

---

# Key Exam Tip

When Power BI needs a different presentation layer without modifying source tables:

| Requirement | Solution |
|---|---|
| Rename columns without changing source | ✅ View |
| Improve query storage performance | Columnstore index |
| Organize database objects | Schema |
| Return calculated table results | Table-valued function |

When the question says:

- "Change column names in the report"
- "Do not modify the underlying table"
- "Create a warehouse object"

Think:

✅ **Create a view**

---

# Question 44

## Question

You have a table named **Sales** that contains the following columns:

- Order_ID
- Customer_ID
- Product_ID
- Quantity
- Sales_Date

You need to write a SQL statement to find the **total number of products sold for each Product_ID in January 2024**.

**What should you run?**

> Select only one answer.

- 
```sql
SELECT Product_ID, COUNT(*)

FROM Sales

WHERE Sales_Date BETWEEN '2024-01-01' AND '2024-01-31'

GROUP BY Product_ID
```

- 
```sql
SELECT Product_ID, COUNT(Quantity)

FROM Sales

WHERE Sales_Date LIKE '2023-01-%'

GROUP BY Product_ID
```

- 
```sql
SELECT Product_ID, SUM(Quantity)

FROM Sales

WHERE MONTH(Sales_Date) = 1 AND YEAR(Sales_Date) = 2024

GROUP BY Product_ID
```

- 
```sql
SELECT Product_ID, SUM(Quantity)

FROM Sales

WHERE Sales_Date > '2024-01-01' AND Sales_Date < '2023-01-31'

GROUP BY Product_ID
```

---

# Answer

✅ **Option 3**

```sql
SELECT Product_ID, SUM(Quantity)

FROM Sales

WHERE MONTH(Sales_Date) = 1 
AND YEAR(Sales_Date) = 2024

GROUP BY Product_ID
```

---

# Explanation

The correct answer is **Option 3** because the requirement is to find the **total number of products sold**, which means you need to add the values in the **Quantity** column.

The correct aggregation is:

```sql
SUM(Quantity)
```

not `COUNT(*)`.

The query:

```sql
SELECT Product_ID, SUM(Quantity)
FROM Sales
WHERE MONTH(Sales_Date) = 1 
AND YEAR(Sales_Date) = 2024
GROUP BY Product_ID
```

does the following:

1. Filters records where:
   - Month = January
   - Year = 2024

2. Groups sales by:

```sql
Product_ID
```

3. Calculates the total quantity sold:

```sql
SUM(Quantity)
```

Example result:

| Product_ID | Total Sold |
|---|---:|
| P001 | 250 |
| P002 | 430 |

---

# Why the other options are incorrect

## ❌ Option 1

```sql
SELECT Product_ID, COUNT(*)
FROM Sales
WHERE Sales_Date BETWEEN '2024-01-01' AND '2024-01-31'
GROUP BY Product_ID
```

- `COUNT(*)` counts the number of sales transactions.
- It does not calculate the total number of products sold.
- A single order may contain multiple products, so counting rows gives incorrect totals.

---

## ❌ Option 2

```sql
SELECT Product_ID, COUNT(Quantity)
FROM Sales
WHERE Sales_Date LIKE '2023-01-%'
GROUP BY Product_ID
```

Problems:

- Filters January **2023**, not January **2024**.
- `COUNT(Quantity)` counts records with values, not the total quantity sold.

---

## ❌ Option 4

```sql
SELECT Product_ID, SUM(Quantity)
FROM Sales
WHERE Sales_Date > '2024-01-01' 
AND Sales_Date < '2023-01-31'
GROUP BY Product_ID
```

Problems:

- The date range is invalid because the start date is later than the end date.
- It would return no records.

---

# Key Exam Tip

SQL aggregation:

| Requirement | Function |
|---|---|
| Total amount/items sold | ✅ `SUM()` |
| Number of rows/orders | `COUNT(*)` |
| Average value | `AVG()` |
| Highest value | `MAX()` |
| Lowest value | `MIN()` |

When the question says:

- "total number of products sold"
- "total quantity"
- "sales volume"

Think:

✅ **SUM(Quantity) + GROUP BY Product_ID**

# Question 45

## Question

You have a **Fabric warehouse**.

You are writing a T-SQL statement to retrieve data from a table named **Sales** to display the highest sales amount for specific customers.

```sql
SELECT CustomerKey,
       SalesAmount,
       <target1> OVER(ORDER BY SalesAmount DESC) AS Ranking

FROM dbo.Sales

WHERE CustomerKey IN (1, 2, 3)
```

You need to ensure that after ties for **SalesAmount**, the next Sales amount increments the **Ranking** value by one.

The following is an example of the expected result:

| CustomerKey | SalesAmount | Ranking |
|---|---:|---:|
| 1 | 100 | 1 |
| 2 | 100 | 1 |
| 1 | 80 | 2 |

**Which function should you use for `<target1>` in the T-SQL statement?**

---

# Answer

✅ **DENSE_RANK()**

---

# Explanation

The correct answer is:

```sql
DENSE_RANK()
```

The completed query is:

```sql
SELECT CustomerKey,
       SalesAmount,
       DENSE_RANK() OVER(ORDER BY SalesAmount DESC) AS Ranking

FROM dbo.Sales

WHERE CustomerKey IN (1, 2, 3)
```

`DENSE_RANK()` assigns ranking values based on the ordered values:

- Highest SalesAmount gets rank 1.
- Equal values receive the same rank.
- The next distinct value receives the next consecutive rank.

Example:

| SalesAmount | DENSE_RANK |
|---:|---:|
| 100 | 1 |
| 100 | 1 |
| 80 | 2 |

This matches the required output.

---

# Why the other ranking functions are incorrect

## ❌ RANK()

Example:

```sql
RANK() OVER(ORDER BY SalesAmount DESC)
```

Result:

| SalesAmount | Rank |
|---:|---:|
| 100 | 1 |
| 100 | 1 |
| 80 | 3 |

`RANK()` leaves gaps after ties. Since two records share rank 1, the next rank becomes 3.

---

## ❌ ROW_NUMBER()

Example:

```sql
ROW_NUMBER() OVER(ORDER BY SalesAmount DESC)
```

Result:

| SalesAmount | Row Number |
|---:|---:|
| 100 | 1 |
| 100 | 2 |
| 80 | 3 |

`ROW_NUMBER()` gives every row a unique number and does not handle ties.

---

## ❌ NTILE()

- Divides rows into a specified number of groups.
- It is used for distribution analysis, not ranking values.

---

# Key Exam Tip

SQL ranking functions:

| Function | Handles ties | Leaves gaps |
|---|---|---|
| `ROW_NUMBER()` | ❌ No | ❌ No |
| `RANK()` | ✅ Yes | ✅ Yes |
| `DENSE_RANK()` | ✅ Yes | ❌ No |
| `NTILE()` | Groups rows | N/A |

When the question says:

- "Same rank for ties"
- "No skipped ranking numbers"
- "Next rank increments by one"

Think:

✅ **DENSE_RANK()**

---

# Question 46

## Question

You have a **Fabric semantic model** that contains a fact table named **Sales**.

Sales contains one row per transaction line and the following columns:

- Sales[OrderDate]
- Sales[Quantity]
- Sales[Price]
- Sales[Cost]

You need to create a DAX measure named **Total Profit** that meets the following requirements:

- Calculates profit per transaction line.
- Aggregates correctly when used in visuals sliced by fields such as product and date.

**Which expression should you use?**

> Select only one answer.

- 
```DAX
Total Profit =
COUNTROWS(Sales[Quantity] * (Sales[Price] - Sales[Cost]))
```

- 
```DAX
Total Profit =
FILTER(Sales, Sales[Quantity] * (Sales[Price] - Sales[Cost]))
```

- 
```DAX
Total Profit =
SUM(Sales[Quantity]) * (SUM(Sales[Price]) - SUM(Sales[Cost]))
```

- 
```DAX
Total Profit =
SUMX(Sales, Sales[Quantity] * (Sales[Price] - Sales[Cost]))
```

---

# Answer

✅ **Option 4**

```DAX
Total Profit =
SUMX(Sales, Sales[Quantity] * (Sales[Price] - Sales[Cost]))
```

---

# Explanation

The correct answer is **SUMX** because profit must be calculated **for each transaction line first**, then aggregated.

The formula:

```DAX
SUMX(
    Sales,
    Sales[Quantity] * (Sales[Price] - Sales[Cost])
)
```

works by:

1. Iterating through every row in the Sales table.
2. Calculating profit for each transaction line:

```
Profit = Quantity × (Price - Cost)
```

3. Adding all transaction-level profits together.

Example:

| Quantity | Price | Cost | Profit |
|---:|---:|---:|---:|
| 2 | 100 | 60 | 80 |
| 5 | 50 | 30 | 100 |

Total Profit:

```
80 + 100 = 180
```

This also works correctly when the report is filtered by:

- Product
- Date
- Customer
- Region

because the measure respects the current filter context.

---

# Why the other options are incorrect

## ❌ COUNTROWS

```DAX
COUNTROWS(Sales[Quantity] * (Sales[Price] - Sales[Cost]))
```

- `COUNTROWS()` counts rows in a table.
- It does not calculate or aggregate profit values.
- The expression is also invalid because the argument is not a table.

---

## ❌ FILTER

```DAX
FILTER(Sales, Sales[Quantity] * (Sales[Price] - Sales[Cost]))
```

- `FILTER()` returns a filtered table.
- It is not an aggregation function.
- It cannot directly produce a profit measure.

---

## ❌ SUM calculation

```DAX
SUM(Sales[Quantity]) * 
(SUM(Sales[Price]) - SUM(Sales[Cost]))
```

- This calculates totals separately and then multiplies them.
- It does not calculate profit at the transaction-line level.

Example problem:

| Qty | Price | Cost |
|---:|---:|---:|
| 10 | 100 | 60 |
| 5 | 200 | 150 |

Correct:

```
(10 × 40) + (5 × 50) = 650
```

Incorrect aggregation:

```
SUM(Qty) × (SUM(Price)-SUM(Cost))
= 15 × (300-210)
= 1350
```

---

# Key Exam Tip

DAX iterators:

| Function | Purpose |
|---|---|
| `SUM()` | Adds values from one column |
| `SUMX()` | ✅ Calculates an expression row-by-row, then sums |
| `COUNTROWS()` | Counts rows |
| `FILTER()` | Returns filtered tables |

When the question says:

- "Calculate per row"
- "Then aggregate"
- "Transaction-level calculation"

Think:

✅ **SUMX()**

---

# Question 47

## Question

You have a **Fabric warehouse** that contains a table named **customer_info**.

The table contains the following columns:

- customer_id
- name
- email
- join_date

The warehouse also contains a table named **order_info**.

The table contains the following columns:

- order_id
- customer_id
- order_total
- order_date

You need to write a SQL query that returns **all the customers who have not yet placed an order (purchased).**

**Which SQL query should you run?**

> Select only one answer.

- 
```sql
SELECT customer_info.name

FROM customer_info

JOIN order_info 
ON customer_info.customer_id = order_info.customer_id

WHERE order_info.order_id IS NOT NULL
```

- 
```sql
SELECT name

FROM customer_info

INNER JOIN order_info 
ON customer_info.customer_id = order_info.customer_id

WHERE order_info.order_id IS NULL
```

- 
```sql
SELECT name

FROM customer_info

LEFT JOIN order_info 
ON customer_info.customer_id = order_info.customer_id

WHERE order_info.order_id IS NULL
```

- 
```sql
SELECT name

FROM customer_info

WHERE customer_id IN

     ( SELECT customer_id

       FROM order_info )
```

---

# Answer

✅ **Option 3**

```sql
SELECT name

FROM customer_info

LEFT JOIN order_info 
ON customer_info.customer_id = order_info.customer_id

WHERE order_info.order_id IS NULL
```

---

# Explanation

The correct answer is **LEFT JOIN with a NULL check** because the requirement is to find customers who **do not have matching records** in the order table.

The logic is:

1. Start with all customers from `customer_info`.
2. Match orders using `customer_id`.
3. Keep customers even when no order exists.
4. Filter only rows where the order is missing.

The result identifies customers who have never purchased.

Example:

### customer_info

| customer_id | name |
|---|---|
| 1 | John |
| 2 | Mary |
| 3 | Alex |

### order_info

| order_id | customer_id |
|---|---|
| 100 | 1 |
| 101 | 2 |

After LEFT JOIN:

| name | order_id |
|---|---|
| John | 100 |
| Mary | 101 |
| Alex | NULL |

Filtering:

```sql
WHERE order_info.order_id IS NULL
```

returns:

| name |
|---|
| Alex |

---

# Why the other options are incorrect

## ❌ Option 1

```sql
JOIN order_info
WHERE order_info.order_id IS NOT NULL
```

- This is an inner join.
- It only returns customers who **have placed orders**.
- It does the opposite of the requirement.

---

## ❌ Option 2

```sql
INNER JOIN order_info
WHERE order_info.order_id IS NULL
```

- An inner join only returns matching records.
- Since matched records always have an order, `order_id IS NULL` will return no results.

---

## ❌ Option 4

```sql
WHERE customer_id IN
(
 SELECT customer_id
 FROM order_info
)
```

- This returns customers who **have placed orders**.
- It identifies purchasers, not customers without purchases.

---

# Key Exam Tip

Finding records missing from another table:

| Requirement | SQL Pattern |
|---|---|
| Find customers with orders | INNER JOIN |
| Find customers without orders | ✅ LEFT JOIN + `WHERE right_table.key IS NULL` |
| Find unmatched records | LEFT ANTI JOIN equivalent |

When the question says:

- "Customers who have not purchased"
- "Records missing from another table"
- "No matching rows"

Think:

✅ **LEFT JOIN + IS NULL**

# Answers

✅ **Add CustomerData and TransactionData tables.**

---

# Question 50

## Question

You have a Fabric tenant that contains a workspace named **Workspace1**.

Workspace1 contains:

- A lakehouse
- A data pipeline
- A notebook
- Several Microsoft Power BI reports

A user named **User1** plans to use **SQL** to access the lakehouse to analyze data.

User1 must have the following access:

- User1 must have **read-only access** to the lakehouse.
- User1 must **NOT** be able to access the rest of the items in Workspace1.
- User1 must **NOT** be able to use Spark to query the underlying files in the lakehouse.

You need to configure access for User1.

**What should you do?**

> Select only one answer.

- Add User1 to the workspace as a member, share the lakehouse with User1, and select **Read all SQL Endpoint data**.
- Add User1 to the workspace as a viewer, share the lakehouse with User1, and select **Read all SQL Endpoint data**.
- Share the lakehouse with User1 directly and select **Build reports on the default dataset**.
- Share the lakehouse with User1 directly and select **Read all SQL Endpoint data**.

---

# Answer

✅ **Share the lakehouse with User1 directly and select Read all SQL Endpoint data.**

---

# Explanation

The correct answer is:

✅ **Share the lakehouse with User1 directly and select Read all SQL Endpoint data.**

This option satisfies all requirements:

### 1. Read-only access to the lakehouse

The **Read all SQL Endpoint data** permission allows User1 to query the lakehouse through the **SQL analytics endpoint**.

User1 can:

- Run SQL queries.
- Analyze lakehouse data.

User1 cannot modify the lakehouse data.

---

### 2. No access to other workspace items

Sharing the lakehouse directly gives access only to that specific item.

User1 will not gain access to:

- Notebooks
- Data pipelines
- Other Power BI reports
- Other workspace content

---

### 3. No Spark access

Spark access requires permissions to interact with the lakehouse files through workspace roles or item permissions that allow notebook/Spark usage.

By granting only SQL endpoint read access, User1 can query the SQL endpoint without accessing the underlying files through Spark.

---

# Why the other options are incorrect

## ❌ Add User1 as a member + share lakehouse

- Workspace **Member** permissions provide broad access.
- User1 would be able to access and potentially modify other workspace items.
- This violates least privilege.

---

## ❌ Add User1 as a viewer + share lakehouse

- Viewer role grants access to the entire workspace.
- User1 would be able to see other workspace items.
- The requirement states User1 must not access the rest of Workspace1.

---

## ❌ Share lakehouse + Build reports on the default dataset

- This permission is related to creating reports from a semantic model.
- It does not provide SQL access to lakehouse data.

# Key Exam Tip

Microsoft Fabric lakehouse permissions:

| Requirement | Permission |
|---|---|
| SQL read-only access to lakehouse | ✅ Read all SQL Endpoint data |
| Access only one item | Share item directly |
| Avoid workspace-wide access | Do not assign workspace roles |
| Create reports from semantic model | Build reports permission |

When the question says:

- "Only access the lakehouse"
- "Use SQL endpoint"
- "No Spark access"
- "Least privilege"

Think:

✅ **Direct lakehouse sharing + Read all SQL Endpoint data**
