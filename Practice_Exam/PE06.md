# Question 51

## Question

Your company uses **Microsoft Fabric** to manage data analytics solutions.

The marketing department needs to share reports with **external partners**.

You need to ensure that reports can be shared with external partners **without compromising sensitive data**.

**Each correct answer presents part of the solution. Which three actions should you take?**

> Select all answers that apply.

- Assign external partners a Viewer role.
- Implement row-level security.
- Restrict workspace sharing settings.
- Share reports via email attachments.
- Set data source credentials to a fixed identity.
- Configure a Power BI app.

---

# Answers

✅ **Implement row-level security.**  
✅ **Restrict workspace sharing settings.**  
✅ **Configure a Power BI app.**

---

# Explanation

The correct actions are:

## ✅ Implement row-level security (RLS)

Row-level security ensures that external partners only see the data they are authorized to view.

Example:

- Partner A → Only sees Partner A sales data.
- Partner B → Only sees Partner B sales data.

RLS protects sensitive information while allowing the same report to be shared with multiple audiences.

---

## ✅ Restrict workspace sharing settings

Restricting sharing settings helps prevent unauthorized sharing of Fabric and Power BI content.

This ensures that:

- Only approved users can share content.
- External sharing follows organizational security policies.
- Sensitive reports are not accidentally exposed.

---

## ✅ Configure a Power BI app

A Power BI app provides a controlled way to distribute reports to users.

Benefits:

- Centralized report distribution.
- Controlled permissions.
- Consumers can view reports without accessing the workspace directly.

This is the recommended approach for sharing reports with business users and external audiences.

---

# Why the other options are incorrect

## ❌ Assign external partners a Viewer role

- Viewer is a workspace role.
- It grants access to the entire workspace.
- External partners should generally consume reports through an app instead of being added to the workspace.

---

## ❌ Share reports via email attachments

- Email attachments create copies of reports/data.
- They can expose sensitive information.
- They are difficult to control and audit.

---

## ❌ Set data source credentials to a fixed identity

- Fixed identity credentials are related to data source access and refresh.
- They do not control which report users can see which data.
- Security should be handled through permissions and RLS.

---

# Key Exam Tip

For secure external report sharing:

| Requirement | Solution |
|---|---|
| Limit data visibility | ✅ Row-level security |
| Controlled distribution | ✅ Power BI app |
| Prevent unauthorized sharing | ✅ Restrict sharing settings |
| Avoid broad access | Do not assign workspace roles |

When the question mentions:

- External partners
- Sensitive data
- Share reports securely

Think:

✅ **RLS + Power BI App + Sharing restrictions**

---

# Question 52

## Question

Your organization uses **Microsoft Fabric** for data analytics.

The team must protect sensitive data in a **Fabric data warehouse** from unauthorized access.

You need to:

- Limit data access based on different user roles.
- Follow the **principle of least privilege**.

**Which two actions should you take to achieve this solution?**

> Select all answers that apply.

- Implement column-level security.
- Assign workspace roles.
- Implement row-level security.
- Set item-level permissions.
- Use dynamic data masking.

---

# Answers

✅ **Implement column-level security.**  
✅ **Implement row-level security.**

---

# Explanation

The correct answers are:

1. **Implement column-level security (CLS)**
2. **Implement row-level security (RLS)**

These security features are designed to restrict access to sensitive warehouse data at a granular level while allowing different users to access only the information they need.

---

## ✅ Implement column-level security

Column-level security controls access to specific columns.

Example:

A warehouse table:

| CustomerID | Name | Email | Salary |
|---|---|---|---|

You can allow regular users to view:

- CustomerID
- Name

while restricting access to:

- Salary
- Sensitive information columns

This follows least privilege by exposing only required data.

---

## ✅ Implement row-level security

Row-level security restricts which rows a user can access based on their role or identity.

Example:

- Sales Manager A → Only sees Region A sales.
- Sales Manager B → Only sees Region B sales.

RLS ensures users can analyze data while only viewing authorized records.

---

# Why the other options are incorrect

## ❌ Assign workspace roles

- Workspace roles (Admin, Member, Contributor, Viewer) control access at the workspace level.
- They are broader permissions and do not provide granular data filtering.
- Assigning workspace roles may violate the principle of least privilege.

---

## ❌ Set item-level permissions

- Item permissions control access to Fabric items such as:
  - Warehouses
  - Lakehouses
  - Reports

- They do not control access to specific rows or columns inside warehouse tables.

---

## ❌ Use dynamic data masking

- Dynamic data masking hides sensitive values by replacing them with masked representations.
- It does not provide role-based filtering of rows or columns.
- Users may still have access to the underlying data depending on permissions.

---

# Key Exam Tip

Fabric Warehouse security:

| Requirement | Feature |
|---|---|
| Restrict specific rows by user/role | ✅ Row-level security |
| Restrict specific columns | ✅ Column-level security |
| Hide sensitive values | Dynamic data masking |
| Control workspace/item access | Workspace roles / item permissions |

When the question says:

- "Different user roles"
- "Limit data access"
- "Least privilege"
- "Warehouse data"

Think:

✅ **RLS + Column-level security**

---

# Question 53

## Question

You have a semantic model that loads data from an **Azure SQL database** and is synced via **Fabric deployment pipelines** to three workspaces named:

- Development
- Test
- Production

You need to reduce the size of the **query requests sent to the Azure SQL database** when **full semantic model refreshes** occur in the Development or Test workspaces.

**What should you do for the deployment pipeline?**

> Select only one answer.

- Add a parameter to filter the data.
- Configure row-level security (RLS).
- Connect either workspace to an Azure Data Lake Storage Gen2 account.
- Configure incremental refresh.

---

# Answer

✅ **Add a parameter to filter the data.**

---

# Explanation

The correct answer is **Add a parameter to filter the data** because deployment pipelines support using **parameters** to apply different configurations across environments.

In this scenario:

- Development and Test environments do not need the entire production dataset.
- A parameter can be used to filter the data source query.
- The filter reduces the amount of data retrieved from Azure SQL during refresh operations.

Example:

### Development

```text
Load only last 3 months of sales data
```

### Test

```text
Load only last 12 months of sales data
```

### Production

```text
Load all historical sales data
```

This reduces the query size sent to Azure SQL while allowing each environment to use the appropriate amount of data.

---

# Why the other options are incorrect

## ❌ Configure row-level security (RLS)

- RLS controls what users can see after authentication.
- It does not reduce the amount of data retrieved during semantic model refresh.
- Refresh operations are performed independently of report user filters.

---

## ❌ Connect either workspace to an Azure Data Lake Storage Gen2 account

- ADLS Gen2 is a storage solution.
- It does not reduce Azure SQL query request size during semantic model refresh.
- It does not solve environment-specific data filtering.

---

## ❌ Configure incremental refresh

- Incremental refresh reduces the amount of data processed by refreshing only new or changed partitions.
- However, the requirement specifically mentions reducing query requests during **full semantic model refreshes in Development and Test**.
- Deployment pipeline parameters are the appropriate solution for loading different data volumes per environment.

---

# Key Exam Tip

Fabric deployment pipelines:

| Requirement | Solution |
|---|---|
| Different data volumes per environment | ✅ Parameters |
| Limit user data visibility | RLS |
| Refresh only recent changes | Incremental refresh |
| Store large datasets externally | ADLS Gen2 |

When the question mentions:

- Development/Test need smaller datasets
- Production needs full data
- Reduce source query size

Think:

✅ **Use deployment parameters to filter data**

---

# Question 54

## Question

You have a Fabric workspace named **Sales-Prod** that is assigned to a **Fabric capacity**.

The workspace contains a semantic model named **SalesModel** that is used by production Microsoft Power BI reports.

Users of an **external tool** cannot deploy metadata changes to **SalesModel**.

**What should you configure?**

> Select only one answer.

- Grant the external tool users the Admin role on the workspace.
- Enable the tenant setting that allows users to create Fabric items.
- Set the XMLA endpoint to Read Write on the capacity that hosts the workspace.
- Download the semantic model as a PBIX file and republish the file to the workspace.

---

# Answer

✅ **Set the XMLA endpoint to Read Write on the capacity that hosts the workspace.**

---

# Explanation

The correct answer is **Set the XMLA endpoint to Read Write** because external tools use the **XMLA endpoint** to connect to and modify semantic model metadata.

When the XMLA endpoint is configured as **Read Write**, external tools such as:

- Tabular Editor
- SQL Server Management Studio (SSMS)
- Other Analysis Services-compatible tools

can perform metadata operations on Power BI semantic models.

Examples of metadata changes include:

- Creating or modifying measures.
- Updating relationships.
- Changing model properties.
- Managing calculation groups.

For production semantic models hosted on Fabric capacity, the capacity setting must allow write operations.

---

# Why the other options are incorrect

## ❌ Grant the external tool users the Admin role on the workspace

- Workspace Admin permissions alone do not enable metadata write operations through external tools.
- The XMLA endpoint must also allow write access.

---

## ❌ Enable the tenant setting that allows users to create Fabric items

- This controls whether users can create Fabric items.
- It does not enable external tool access to semantic model metadata.

---

## ❌ Download the semantic model as a PBIX file and republish the file to the workspace

- Republishing a PBIX replaces the model rather than allowing external tools to deploy metadata changes.
- It is not the recommended approach for metadata management in a production semantic model.

---

# Key Exam Tip

Power BI/Fabric external tool access:

| Requirement | Solution |
|---|---|
| View semantic model metadata | XMLA endpoint = Read Only |
| Modify semantic model metadata | ✅ XMLA endpoint = Read Write |
| Create Fabric items | Tenant setting |
| Manage workspace permissions | Workspace roles |

When the question mentions:

- External tools
- Metadata changes
- Semantic model modification

Think:

✅ **Enable XMLA endpoint Read Write on the capacity**

---

# Question 55

## Question

You have a Fabric workspace named **Workspace1** that contains:

- A semantic model
- A report

You plan to connect **Workspace1** to a Git repository named **Repo1** and enable version control.

Repo1 will be used to manage and maintain the contents of Workspace1.

You need to ensure that other users can collaborate on the semantic model and the report.

The solution must minimize development effort.

**What should you do?**

> Select only one answer.

- Commit the contents of Repo1.
- Create a Microsoft Power BI Desktop project and add the project to Repo1.
- Create a new workspace and connect the new workspace to a local folder.
- From Workspace1, create a branch and a new workspace.

---

# Answer

✅ **From Workspace1, create a branch and a new workspace.**

---

# Explanation

The correct answer is:

✅ **From Workspace1, create a branch and a new workspace.**

Microsoft Fabric Git integration supports collaborative development by allowing users to:

1. Connect a workspace to a Git repository.
2. Create branches for separate development work.
3. Create new workspaces associated with branches.

This allows multiple developers to work independently on:

- Semantic models
- Reports
- Other Fabric items

while maintaining version control and minimizing manual setup.

The workflow is:

```
Main Workspace
        |
        |
      Git Repo
        |
   Create Branch
        |
 New Development Workspace
        |
 Collaborate and Commit Changes
```

---

# Why the other options are incorrect

## ❌ Commit the contents of Repo1

- Committing stores changes in Git.
- However, it does not create separate environments for collaboration.
- It does not solve the need for multiple users to work efficiently.

---

## ❌ Create a Microsoft Power BI Desktop project and add the project to Repo1

- PBIP projects support source control for Power BI Desktop projects.
- However, the scenario is about **Fabric workspace Git integration**.
- Manually creating a PBIP project adds unnecessary effort.

---

## ❌ Create a new workspace and connect the new workspace to a local folder

- Fabric Git integration connects workspaces to Git repositories, not local folders.
- This does not provide the intended collaborative workflow.

---

# Key Exam Tip

For Fabric Git collaboration:

| Requirement | Solution |
|---|---|
| Enable version control | Connect workspace to Git |
| Multiple developers | Use Git branches |
| Separate development environments | Create branch + workspace |
| Manual PBIX/PBIP management | Avoid unless required |

When the question mentions:

- Fabric workspace
- Git integration
- Collaboration
- Minimize effort

Think:

✅ **Create a branch and a new workspace**

---

# Question 56

## Question

You have a Fabric workspace that contains a **certified Microsoft Power BI semantic model** named **SalesCore**.

Authors must start new reports that meet the following requirements:

- Contain no embedded data.
- Include company branding.
- Contain a preconfigured slicer placement.
- Have a standard report layout and configuration.

You need to create a reusable report template for the authors.

**What should you create?**

> Select only one answer.

- a Power BI template file (.pbit)
- a Power BI data source file (.pbids)
- a Power BI Project (.pbip) committed to Git
- a Power BI Desktop file (.pbix) linked to Microsoft OneDrive refresh

---

# Answer

✅ **a Power BI template file (.pbit)**

---

# Explanation

The correct answer is:

✅ **Power BI template file (.pbit)**

A **Power BI template file (.pbit)** is designed to provide a reusable report structure without including the actual data.

It stores:

- Report pages and layouts.
- Visual configurations.
- Themes and branding.
- Slicers and filters.
- Data model connection information.

When authors open a `.pbit` file, Power BI prompts them to connect to the required data source or semantic model.

In this scenario, the template can connect to the certified **SalesCore semantic model**, allowing authors to create standardized reports without embedding data.

---

# Why the other options are incorrect

## ❌ Power BI data source file (.pbids)

- A `.pbids` file stores connection information for data sources.
- It does not store:
  - Report layouts.
  - Branding.
  - Visuals.
  - Slicer configurations.

---

## ❌ Power BI Project (.pbip) committed to Git

- A `.pbip` project supports source control and collaboration.
- It is intended for development workflows.
- It is not the simplest solution for distributing reusable report templates.

---

## ❌ Power BI Desktop file (.pbix) linked to Microsoft OneDrive refresh

- A `.pbix` file contains the report and potentially imported data.
- It is not specifically designed as a reusable empty template.
- OneDrive refresh does not address the requirement of no embedded data.

---

# Key Exam Tip

Power BI file types:

| File Type | Purpose |
|---|---|
| `.pbit` | ✅ Reusable report template without data |
| `.pbix` | Complete Power BI report file |
| `.pbids` | Data source connection definition |
| `.pbip` | Project format for source control |

When the question says:

- Reusable report template
- No embedded data
- Standard layout/branding

Think:

✅ **Power BI Template (.pbit)**

---

# Question 58

## Question

You have a **Fabric deployment pipeline** that has the following stages:

- Development
- Test
- Production

The **Development** workspace contains a lakehouse named **SalesLH**.

SalesLH contains an **internal OneLake shortcut** that points to a table in another lakehouse in the same workspace.

You need to deploy **SalesLH** to **Test** by using the deployment pipeline.

**What should you do?**

> Select only one answer.

- Use a Variable Library to remap shortcut targets during the deployment.
- Map the lakehouse dependency in the deployment pipeline to a different upstream lakehouse.
- Enable Git integration for the workspace, so that lakehouse items are tracked in source control.
- Create the tables, folders, and files referenced by the shortcut in the target workspace before the deployment.

### Answer

✅ **Create the tables, folders, and files referenced by the shortcut in the target workspace before the deployment.**

---

### Explanation

In Microsoft Fabric deployment pipelines, **internal OneLake shortcuts** have a dependency on the target data objects they reference.

In this scenario:

- `SalesLH` contains an internal OneLake shortcut.
- The shortcut points to a table in another lakehouse in the same workspace.
- When deploying `SalesLH` to the Test stage, the shortcut target must already exist in the target workspace.

Therefore, before deployment, you must:

1. Create the required lakehouse objects in the Test workspace:
   - Tables
   - Folders
   - Files

2. Deploy `SalesLH`.

This ensures that the shortcut can resolve correctly after deployment.

---

# Why the other options are incorrect

## ❌ Use a Variable Library to remap shortcut targets during the deployment

- Variable Libraries are used for environment-specific configuration values.
- They do not automatically remap internal OneLake shortcut references during deployment.

---

## ❌ Map the lakehouse dependency in the deployment pipeline to a different upstream lakehouse

- Deployment pipeline dependency mapping applies to supported Fabric items.
- It does not resolve internal OneLake shortcut targets.

---

## ❌ Enable Git integration for the workspace

- Git integration provides source control and version history.
- It does not handle shortcut dependencies during deployment.

---

### Key Exam Tip

For Fabric deployment pipelines and OneLake shortcuts:

| Scenario | Solution |
|---|---|
| Shortcut references existing data | ✅ Ensure target tables/files/folders exist first |
| Track workspace changes | Git integration |
| Manage environment variables | Variable Library |
| Promote items | Deployment pipelines |

When deploying lakehouses with internal shortcuts:

✅ **Create the shortcut dependencies in the target workspace before deployment.**

---

# Question 59

## Question

Your organization uses **Microsoft Fabric** for data analytics.

You need to manage the semantic models with **external tools** due to the size.

**What should you do?**

> Select only one answer.

- Enable incremental refresh for the semantic models.
- Enable large semantic model storage format.
- Enable read-only in the XMLA Endpoint settings.
- Enable read-write in the XMLA Endpoint settings.

---

# Answer

✅ **Enable read-write in the XMLA Endpoint settings.**

---

# Explanation

The correct answer is:

✅ **Enable read-write in the XMLA Endpoint settings.**

External tools such as:

- Tabular Editor
- SQL Server Management Studio (SSMS)
- Other Analysis Services-compatible tools

use the **XMLA endpoint** to connect to and manage Power BI/Fabric semantic models.

Because the requirement is to **manage semantic models with external tools**, the XMLA endpoint must allow write operations.

With **XMLA Endpoint = Read Write**, you can perform metadata management tasks such as:

- Modify measures.
- Manage relationships.
- Create calculation groups.
- Update model properties.
- Deploy metadata changes.

---

# Why the other options are incorrect

## ❌ Enable incremental refresh for the semantic models

- Incremental refresh improves refresh performance by processing only new or changed data.
- It does not enable external tool management.

---

## ❌ Enable large semantic model storage format

- Large semantic model storage format allows semantic models larger than the standard size limit.
- It is useful for large datasets but does not provide external tool management capabilities.

---

## ❌ Enable read-only in the XMLA Endpoint settings

- Read-only XMLA allows external tools to inspect metadata.
- It does not allow modifications or management operations.

Example:

| XMLA Setting | Capability |
|---|---|
| Read Only | View metadata |
| Read Write | ✅ Manage and modify semantic models |

---

# Key Exam Tip

When questions mention:

- External tools
- Tabular Editor
- Metadata changes
- Managing semantic models

Think:

✅ **XMLA Endpoint = Read Write**

When questions mention:

- Very large semantic models

Think:

✅ **Large semantic model storage format**
